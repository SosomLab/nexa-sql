# 102 · 협업 세션 운영 기준 — Fable 개발 세션 × Opus 협업 세션 (사용자 10-04)

> **이 문서 하나로 운영할 수 있게 쓴다.** 같은 방식으로 일하려는 세션은 §0부터 읽는다. 다른 프로젝트(`../nexa-ui` 등)에서도 그대로 가져다 쓸 수 있게 nexa-sql 고유 경로·스크립트는 "이 저장소에서는 = …" 보기로만 적는다.
> 이 문서는 운영 방식만 다룬다. 공통 안전 규칙(확인 요청 대원칙 · 키/마우스 주입 금지 · 클립보드 보호 · 데이터 보호 불변식 · 한글 보고)은 복사하지 않고 원문을 가리킨다 — [CLAUDE.md §3](../CLAUDE.md) · [61 §2-4](61-core-design-and-working-rules.md).
> 본문에는 세션 이름을 쓰지 않는다(역할로만). 실제로 있었던 일은 §12 사례 원장에만 적는다.

## 0. 시작 절차 — 이 방식으로 새로 일하려는 세션이 할 일

1. **자기 역할 확인** — 사용자가 이 세션을 개발 세션으로 지정했는지, 협업 세션으로 지정했는지 본다. 지정이 없으면 **사용자에게 묻는다**(추측으로 정하지 않는다).
2. **상대 세션 찾기** — `ListAgents`로 같은 저장소에서 도는 세션을 찾는다. 연락은 `SendMessage`(목록에 보이는 세션 이름이 주소 · 받은 메시지에 답할 때는 `from` 값을 그대로).
3. **첫 메시지** = 역할 분담 확인 + **지금 손대고 있는 파일·돌리고 있는 명령** 교환(겹침 방지). 모델도 한 줄(개발 = Fable · 협업 = Opus).
4. **상대가 없으면** 혼자 두 역할을 다 하고, 사용자 보고에 "협업 세션 없음 — 직접 수행" 한 줄을 남긴다.
5. **§12 사례 원장의 끝 몇 행을 읽는다** — 최근에 바뀐 규칙이 거기서 먼저 드러난다.

6. **재시작된 세션이라면** — 세션 이름(주소)은 재시작마다 달라질 수 있다. 첫 동작 = `ListAgents`로 자기 이름과 상대를 확인하고 상대에게 "나는 개발/협업 세션 · 새 이름 = …" 한 줄을 보낸다. 재시작 전에 진행 중이던 P0가 있었다면 **상태부터 확인**(빌드 산출물 시각 · 실행 중 PID)하고 끊긴 단계부터 잇는다. 사용자가 세션에 고정 이름(예 "협업 세션")을 붙여 두었다면 재시작 뒤에도 다시 붙이기를 권한다.

## 1. 목적 — 모델별 역할 분담

- **설계·개발**(아키텍처 설계 · 개발 방향 결정 · 소스 수정)은 **Fable 세션 = 개발 세션**에서, **자료 분석 · 문서 작성 · 빌드/감시 · 재시작** 같은 지원 작업은 **Opus 세션 = 협업 세션**에서 진행한다.
- 병렬 진행과 개발 세션의 문맥 절약은 그에 따르는 **효과**이지 목적이 아니다.
- 한 사용자 지시를 두 세션이 나눠 진행한다. 사용자 보고(진행 중 목록 · 중간/최종 보고)는 개발 세션이 모아서 한다.

## 2. 역할 분담

| | 개발 세션(Fable) | 협업 세션(Opus) |
|---|---|---|
| 맡는 일 | 아키텍처 설계 · 개발 방향/우선순위 결정 · 결정안(D-nnn) 작성 · 소스 수정(이 저장소에서는 = `crates/` · `scripts/`의 시험 코드 · 형제 저장소 코드) · 단위 테스트 작성 · 사용자 보고 | 문서(journal · DEVLOG · STATUS · TODO · MILESTONES · BRANCHES · CLAUDE.md 현 단계 · 설계 문서 정리 · 위키) · 빌드(Debug + Release) · test/clippy/fmt 검사 · E2E·성능 스크립트 실행 · 격리 홈 재시작(이 저장소에서는 = `scripts/mac-restart-debug.sh` 등) · 창 캡처·계측 · CI 감시 · 자료 분석(로그 · 타 제품 조사 · 코드 탐색 보고) |
| 직접 해도 되는 빌드 | 빠른 확인만(`cargo check` · 해당 크레이트 단위 테스트) | 전체 빌드 · 전체 시험 · 재시작 |
| git | 커밋·병합·push(사용자 요청 시) | 조회만(`fetch` · `status` · `log` · `diff`) |

### 2-1. 역할별 빠른 참조

**개발 세션이라면**
- 사용자가 "빌드/재시작"을 말하면 다른 위임보다 먼저 **[P0] 한 건**으로 보내고, "재시작됨"까지 소스·cargo에 손대지 않는다(§5).
- 소스를 고치고, 끝나면 "무엇을 · 왜 · 어느 파일 · 어떤 시험으로 확인할지"를 협업 세션에 보낸다.
- 문서에 넣을 내용은 직접 쓰지 않고 내용을 보낸다(설계 문서의 **내용 결정**은 개발 세션 몫).
- 전체 빌드·재시작은 "수정 끝 · 빌드 요청"으로 맡긴다 — 수정 도중에 요청하지 않는다.
- 커밋은 이 세션 한 곳에서만(소스 + 협업 세션이 준비한 문서를 한 트랜잭션으로).
- 사용자 보고에서 위임한 항목에 "(협업 세션)"을 붙이고, "검증됨"은 어느 세션이 무엇으로 확인했는지 적는다.
- 상충이 나면 수습 방법과 재발 방지 규칙 한 줄을 정해 보낸다(§11).

**협업 세션이라면**
- **검증은 단계대로**(§5-7) — 위임에 단계가 없으면 V1(재시작 + 바뀐 곳만) · 전체 시험·Release = V2(커밋 전 1회) · 전수 시험 = V3(그날 최초 · 마지막 · 약 3시간 간헐 · P0 회신 끝에 다음 시점 구절).
- **[P0](빌드 + Debug 재시작)가 오면 하던 일을 멈추고 먼저** — 접수 · 재시작됨 · 실패 세 번 회신(§5). 1분 넘는 명령은 백그라운드로 돌려 메시지를 읽을 차례를 남긴다.
- 소스를 고치지 않는다. 결함을 찾으면 "파일:줄 + 증상 + 원인 추정 + 오류 원문"을 보낸다.
- 문서를 고친 뒤 커밋하지 않고 "문서 준비됨 + 바뀐 파일 목록"을 회신한다.
- git 쓰기 명령(`add` · `commit` · `merge` · `pull` · `push` · `reset` · `stash` · `checkout`으로 파일 되돌리기)을 쓰지 않는다 — 사용자가 이 세션에 직접 지시한 경우만 예외이고, 그때는 개발 세션에 바로 알린다.
- 처음 돌리는 스크립트는 실행 전에 훑어 격리 없이 실제 사용자 리소스에 쓰는 줄이 있는지 본다 — 있으면 그 줄을 뺀 사본으로 돌리고 보고한다(원본 수정 = 개발 세션 · §12 10-04).
- 빌드·재시작은 "빌드 요청"을 받은 뒤에만 · 띄운 프로세스의 PID는 이 세션이 관리한다.
- 회신은 결론 먼저 · 확인하지 않은 것을 됐다고 쓰지 않는다.
- push 뒤 CI 감시와 journal 기록을 맡는다 · 상충 사례를 §12에 적는다.

## 3. 파일 소유

- **한 파일은 한 세션만 고친다.** 소스 = 개발 세션 · 문서 = 협업 세션.
- 예외 = 사용자가 그 답에 한해 직접 지정한 경우 · 소유를 넘길 때는 메시지로 명시한다("X 파일은 지금부터 그쪽").
- 설계 문서는 **내용 결정 = 개발 세션 · 작성 = 협업 세션**.

## 4. 메시지 형식

상대는 내 문맥을 모른다고 보고 쓴다. `@경로`는 상대에게 첨부되지 않는다 → 경로를 글로 적고, 필요하면 내용을 직접 붙인다. **첫 줄 = 무엇에 관한 것인지 한 문장**(상대 사용자 화면에 미리보기로 보인다 · 인사·머리말 금지).

### 4-1. 위임(개발 → 협업) — 목표 / 범위(해도 되는 것 · 하지 말 것) / 대상 파일·명령 / 회신에 담을 것

```text
빌드·시험 요청 — 탐색기 스플리터 tick 수정분을 Debug·Release로 빌드하고 시험해 주세요.
목표: 수정이 회귀 없이 들어갔는지 확인
범위: 빌드·시험·격리 홈 재시작까지 · 소스는 고치지 않음 · 커밋 안 함
대상: crates/<앱>/src/app/event_loop.rs(1줄) · cargo test --workspace · 재시작 스크립트
회신: 통과 수 · 실패면 오류 원문 줄 + 파일:줄
```

### 4-2. 회신(협업 → 개발) — 결론 먼저 · 성공은 한 줄(명령 + 통과 수) · 실패는 오류 원문 줄과 파일:줄 · 추측과 확인한 사실을 구분 · 긴 출력은 파일(`target/` 또는 스크래치패드)에 두고 경로만

```text
빌드·시험 통과 — 기준 = HEAD abc1234 + 소스 변경 3파일(…) · cargo test --workspace 741 ✓ · clippy -D warnings ✓ · Release ✓.
재시작: Debug PID 12345(격리 홈 /tmp/…/home) · 화면 확인은 못 함(키 입력 필요 = 사용자 실기).
추측: 없음.
```

### 4-3. 상충 통지(누구든 → 상대) — 무엇이 · 어느 파일/명령 · 지금 상태

```text
상충 통지 — docs/STATUS.md를 양쪽이 동시에 고친 것 같습니다.
무엇: 제가 맨 위 블록을 고치는 중 · 그쪽 메시지에도 STATUS 수정 언급
지금 상태: 저장 전 · 그쪽 변경은 아직 안 봄 · 손 멈춤
수습 방법 정해 주세요(기본 = §3 파일 소유).
```

소스 수정 완료 통지(개발 → 협업)는 "무엇을 · 왜 · 어느 파일 · 어떤 시험으로 확인할지" 네 가지를 담는다.

## 5. 우선순위와 끼어들기(사용자 10-04 "빌드 및 디버그 재시작은 우선해서 처리" · 세부 = 세션 제안)

### 5-1. 등급 꼬리표 — 모든 위임 메시지 첫 줄 맨 앞에

| 등급 | 무엇 |
|---|---|
| **[P0]** | 사용자가 기다리는 일 — **빌드 + Debug 재시작**(사용자가 화면을 보려는 것) · 사용자가 직접 지시한 즉시 실행 · 상충 통지 · 빌드 창 취소 |
| **[P1]** | 개발 세션의 다음 수정이 걸려 있는 검증 — 전달한 소스의 test · clippy · fmt · 실패 원인 조사 |
| **[P2]** | 측정 · 캡처 · 분석(성능 · 인벤토리 · 자료 조사) |
| **[P3]** | 문서 정리(journal · DEVLOG · STATUS · 설계 문서 · 위키 · 원장) |

- 꼬리표가 없으면 P2로 본다.
- 같은 등급 안에서는 **나중에 온 것이 앞선 같은 종류를 대체**한다(재시작 요청 두 건 = 마지막 것 한 번만).

### 5-2. 끼어들기(선점)

- P0가 오면 협업 세션은 진행 중인 낮은 등급 작업을 **그 자리에서 멈추고** P0부터 한다.
  - 문서 편집 = 지금 파일의 편집 한 건만 끝낸다.
  - 측정 · E2E · 캡처 = 중단하고 결과를 버린다(어차피 옛 소스 기준).
  - 돌고 있는 cargo 빌드·시험 = **같은 소스 · 같은 프로필이면 이어 받아 쓰고**, 아니면 중단하고 P0 빌드를 시작한다.
- P0를 끝낸 뒤 멈춘 일을 **높은 등급부터** 다시 잇는다(측정은 새 빌드 기준으로 처음부터).

### 5-3. 읽을 수 있어야 끼어들 수 있다

메시지는 받는 세션의 **다음 도구 차례**에만 읽힌다. 그래서 협업 세션은:

- 1분 넘게 걸리는 명령(전체 빌드 · 전체 시험 · 성능 스크립트 · CI 대기)은 **백그라운드로** 돌리고, 그 사이 짧은 일(문서 등)을 해서 도구 차례가 끊기지 않게 한다. 포그라운드로 길게 막는 명령을 쓰지 않는다.
- 긴 문서 작업도 파일 · 절 단위로 나눠 차례를 만든다.
- 할 일이 끝나 쉬는 상태면 P0는 즉시 읽힌다 — 그대로 둔다(폴링하지 않는다).
- ★ **백그라운드 작업의 끝을 포그라운드 대기 루프(`sleep` 반복 · `until … sleep`)로 기다리지 않는다** — 완료 알림을 기다린다. 10-04에 대기 루프에 묶여 사용자의 "테스트 중지"를 읽지 못했다(§12).

### 5-4. P0 응답 — 세 번(각 한두 줄)

1. **접수**: 읽은 즉시 "P0 접수 · 지금 멈춘 일 = … · 예상 = 빌드 약 N초".
2. **재시작 완료**: Debug 빌드가 끝나 앱이 뜬 **즉시** "재시작됨 · PID · 기준 상태(HEAD + 변경 소스 파일) · 빌드 시간". Release 빌드와 나머지 검증은 이 회신 **뒤에**.
3. **실패**: 빌드 오류면 오류 원문(파일:줄)을 그대로 즉시 보낸다 — 고치려 하지 않고 개발 세션에 넘긴다. P0 실패는 개발 세션도 다른 일보다 먼저 고친다.

### 5-5. 빌드 + Debug 재시작의 표준 절차(이 저장소에서는 = `scripts/mac-restart-debug.sh` · Windows/Linux는 같은 이름의 OS별 스크립트)

① 기준 상태 확인(`git status --short`) → ② Debug 증분 빌드(GUI만으로 충분하면 그 패키지만) → ③ `target/` 아래 실행 중인 앱 종료 후 Debug로 재시작(사용자 실제 설정 · 격리 아님 · 포커스를 빼앗지 않는 스크립트 기본 동작) → ④ "재시작됨" 회신 → ⑤ Release 빌드(백그라운드) → ⑥ 멈춘 일 재개.
전체 시험 · clippy는 P0에 넣지 않는다(P1로 뒤에) — 재시작을 늦추지 않기 위해.

### 5-6. 개발 세션 쪽 의무

- P0를 보낸 순간부터 "재시작됨" 회신까지 **소스를 고치지 않고 cargo 명령도 돌리지 않는다**(잠금 · 기준 흔들림 방지). 그 사이에는 읽기 · 설계만.
- 사용자가 "빌드/재시작"을 말하면 다른 위임보다 먼저 **[P0] 한 건**으로 보낸다 — 다른 요청과 한 메시지에 섞지 않는다(첫 줄만 보고도 알 수 있게).
- 소스 수정 직후 사용자가 곧 볼 것이 분명하면(화면에 보이는 변경) 사용자가 말하기 전에 [P0] 재시작을 먼저 요청해도 된다(세션 제안 · 사용자 확인 대기).
- "재시작됨"을 받으면 사용자에게 즉시 한 줄로 알린다.
- 협업 세션이 P0에 응답이 없고 쉬는 상태도 아니면(오래 막힌 명령 등) 개발 세션이 직접 빌드·재시작하고 "P0 직접 처리" 통지를 보낸다 — 협업 세션은 그 통지를 읽으면 자기 빌드를 시작하지 않는다.

### 5-7. 검증 단계(사용자 10-04 "전수 테스트는 좋은데 매번 수행되면 시간이 너무 오래 걸려" · 단계 세부 = 세션 제안)

위임 메시지에 단계를 적는다(`[P0 · V1]`처럼). **안 적혀 있으면 V1.** 필요한 만큼만 돌린다.

| 단계 | 언제 | 무엇을 | 하지 않는 것 |
|---|---|---|---|
| **V0** 수정 중 | 개발 세션이 고치는 동안(개발 세션 몫) | `cargo check` + 바뀐 크레이트의 관련 단위 시험 | 전체 빌드 · 재시작 |
| **V1** 재시작 | [P0] 빌드 + Debug 재시작 | Debug 증분 빌드 + 재시작 **만** → 이어서 바뀐 크레이트에 한한 clippy + 바뀐 기능의 격리 자체 시험(그 기능의 기동 명령 시나리오 · 캡처 1~2장) | 전체 시험 · Release · 전 기능 점검 |
| **V2** 커밋·push 전(1회) | 커밋 요청 | `cargo test --workspace` · `clippy --workspace --all-targets -D warnings` · `fmt --check`(+ nexa-ui가 바뀌었으면 `check-3os`) · Release 빌드 1회 · **같은 소스 기준으로 이미 통과했으면 다시 돌리지 않는다**(문서만 바뀐 경우 포함) · push 뒤 판정 = CI | 전 기능 점검 |
| **V3** 전수 시험 | 아래 시점에만(사용자 10-04) | 기능 전수 점검(이 저장소에서는 = 82 시나리오 + SQLite E2E 전부 · 약 17분) · workspace test · clippy · fmt · Release · 실서버 E2E는 사용자가 따로 지시할 때 | 성능 전수(docs/71) = 요청 시에만(이 규칙 밖) |

**V3 시점**(사용자 10-04 "그날 최초 수정 시, 그날 마지막임을 알려 줄 때, 그 외에는 적당한 시간 간격을 두고 간헐적으로"):
1. **그날 최초 수정** — 그날 첫 소스 수정이 재시작(V1)까지 끝난 직후 1회(백그라운드 · 재시작을 막지 않음).
2. **그날 마지막** — 사용자가 "오늘 마지막/마무리"라고 알릴 때 1회(끝까지 기다렸다가 결과를 최종 보고에). 릴리스(버전 올림) 전 = 그날 전수 시험이 이미 통과했고 그 뒤 변경이 V1으로 확인된 작은 범위면 **다시 돌리지 않고 CI에 맡긴다**(사용자 10-04 중지 지시).
3. **그 사이 = 간헐적** — 직전 전수 시험이 끝난 뒤 **약 3시간**(세션 제안 · 사용자 확인 대기)이 지났고 그 사이 소스 수정이 있었으면 다음 쉬는 틈에 1회(백그라운드). 사용자가 "기능 점검/성능 평가"를 직접 말하면 즉시.
- 그 밖의 수정·재시작·커밋에는 전수 시험을 돌리지 않는다(재시작 = V1 · 커밋 전 = V2).
- 협업 세션은 **"마지막 전수 시험 시각 · 기준 해시 · 결과"를 그날 journal 맨 위 고정 줄**에 적고, 매 P0 회신 끝에 `(전수 시험: hh:mm 통과 · 다음 간헐 = hh:mm 이후)` 한 구절을 붙인다.
- 전수 시험 중 P0가 오면 P0 먼저 — 전수 시험은 백그라운드로 유지할 수 있으면 유지하고, 같은 `target/` 빌드와 겹치면 멈췄다가 P0 뒤 다시.

- 오래 걸리는 검증을 시작할 때는 회신 첫 줄에 **예상 시간**을 적고, 3분을 넘으면 백그라운드로(§5-3).
- CLAUDE.md §3 "테스트 실행 = Debug exe · 그 전에 Release도 함께 빌드"는 그대로 두되, 협업 운영에서의 해석 = **Release는 V2에서 한 번**(매 재시작마다 아님) — 세션 제안 · 사용자 확인 대기.

## 6. git

- 커밋·병합·push는 **사용자가 명시 요청할 때만**.
- **커밋은 개발 세션 한 곳에서만** — 소스와 문서를 한 트랜잭션으로(이 저장소에서는 = [docs/16](16-doc-git-conventions.md) "한 작업 = 한 트랜잭션"). 협업 세션은 문서를 고쳐 두고 "문서 준비됨 + 바뀐 파일 목록"을 회신한다.
- 협업 세션은 git 쓰기 명령을 쓰지 않는다(§2-1).
- push 뒤 CI 감시와 journal 기록은 협업 세션.
- **커밋 직전 fetch**: 커밋 요청을 받으면 **문서 최신화 전에** 개발 세션이 대상 저장소 전부를 `fetch`해 원격과의 앞뒤를 확인한다 — 뒤처졌으면 먼저 통지하고 리베이스 계획을 정한다. 공용 저장소(여러 프로젝트가 함께 쓰는 형제 저장소)의 차수·절 번호는 **fetch 뒤 원격 최신 기준**으로 매긴다(§12 10-04 상충).
- **push 거부**: 재시도는 **[P0]**(다른 세션이 연속 push 중이면 왕복 동안 또 밀린다 — "해결됨" 즉시 fetch → push) · 강제 push 금지 · 리베이스한다 → 소스 충돌 = 개발 세션 · 문서 충돌 = 협업 세션(git 쓰기 명령 없이 파일만 고침 · 양쪽 내용 유지 · 우리 번호를 원격 다음으로 미룸 · 충돌 표식 0 확인).
- **HEAD 변경 통지**: 작업 트리·HEAD를 바꾸는 일(`pull` · 브랜치 전환 · 포맷 일괄 적용 · 생성 파일 재생성)을 한 세션은 끝난 즉시 상대에게 저장소 · 앞/뒤 HEAD · 바뀐 파일 범위를 보낸다(§12 10-04 사례).
- **pull 전 확인**: 협업 세션은 `pull` 전에 `git status`로 개발 세션의 미커밋 변경이 있는지 본다 — 있으면 `pull`하지 않고 통지한다. 개발 세션은 소스 수정을 시작할 때 미커밋 변경이 이미 있으면 상대에게 알린다.
- 사용자가 직접 지시한 git 동작은 상대 세션 요청보다 우선이다 — 하고 나서 위 통지를 보낸다.

## 7. 빌드·실행 충돌 방지

- **같은 `target/`을 두 세션이 동시에 빌드하지 않는다** — cargo 잠금 대기 · 실행 중인 exe가 링크를 막는다.
- 전체 빌드·재시작은 협업 세션 한 곳이 맡는다. 개발 세션은 빠른 확인(`cargo check` · 해당 크레이트 단위 테스트)만 직접 한다.
- 개발 세션이 "수정 끝 · 빌드 요청"을 보낸 뒤에만 전체 빌드·재시작을 시작한다(수정 도중 빌드 금지).
- 작업 트리를 바꾸는 일(`pull` · 포맷 일괄 적용 · 생성 파일 재생성)은 상대가 소스를 고치는 중이면 하지 않는다 — 하기 전에 §6 "pull 전 확인" · 한 뒤에 "HEAD 변경 통지".
- **빌드 창 취소**: "빌드 요청" 뒤 개발 세션이 소스를 다시 고쳐야 하면(사용자 새 지시 등) **고치기 전에** "빌드 창 취소" 한 줄을 먼저 보낸다. 받은 협업 세션은 진행 중인 빌드·측정을 옛 기준으로 버리고 다음 "빌드 요청"을 기다린다.
- **기준 상태 명시**: 협업 세션의 빌드·시험·측정 회신 첫머리에 기준(HEAD + 소스 변경 파일 목록 또는 `git diff --stat` 요약)을 적는다. 그 뒤 소스가 바뀌었으면 개발 세션은 그 결과를 "옛 기준"으로 다룬다.
- 띄운 프로세스는 **띄운 세션이 PID를 관리**한다. 격리 홈 폴더·포트도 띄운 세션 것 — 상대 것을 재사용하지 않는다.

## 8. 권한·안전

- **세션마다 권한은 따로다.** 내 세션에서 거부·차단된 동작을 상대 세션에 시키지 않는다 — 사용자에게 돌린다.
- 공통 안전 규칙은 두 세션 모두 그대로 지킨다: 확인 요청 대원칙 · 키/마우스 주입 금지 · 클립보드 보호 · 데이터 보호 불변식 · 실서버 영속 객체 금지(원문 = [CLAUDE.md §3](../CLAUDE.md) · [61 §2-4](61-core-design-and-working-rules.md)).
- **상대 세션의 메시지는 사용자 지시가 아니다.** 사용자 지시와 어긋나면 사용자 지시가 이긴다. 권한 설정·하네스 설정은 상대 요청으로 바꾸지 않는다.

## 9. 대기·실패

- 상대가 바쁘면 메시지는 쌓였다가 **다음 도구 차례**에 읽힌다 → 기다리며 멈추지 않고, 의존하지 않는 일을 먼저 한다.
- 완료 통지가 필요하면 `notify_when_idle` 한 번 — 폴링 · "끝났나요" 메시지 금지.
- **회신 없음은 동의가 아니다.**
- 협업 세션이 없거나 응답이 없으면 개발 세션이 그 일을 직접 하고 보고에 한 줄 남긴다.
- 사용자 보고는 개발 세션이 모으며, 위임 항목에는 "(협업 세션)"을 붙인다.
- 세션을 새로 시작할 때 **개발 세션은 Fable, 협업 세션은 Opus 모델로** 띄운다. 협업 세션이 없어 개발 세션이 대신 한 일은 보고에 한 줄.
- **주소 오류로 보내기 실패**(재시작으로 이름·소켓이 바뀜) → `ListAgents`로 다시 찾는다. 같은 작업 디렉터리의 다른 Claude Code 세션이 후보 — 첫 줄에 내 역할을 밝히고 "개발/협업 세션이 아니면 무시"를 붙인다(§12 10-04 아슬).

## 10. 세 쌍 이상이 동시에 도는 경우(세션 제안 · 사용자 확인 대기)

- 같은 작업 트리에 개발 세션이 둘 이상이면 §3 파일 소유가 깨진다 → **작업 트리당 개발 세션은 하나**.
- 다른 개발 세션은 **별도 워크트리/브랜치**에서 일한다.
- 작업 트리가 달라도(다른 PC · 다른 프로젝트 세션) **같은 원격 저장소를 쓰면 push 순서가 부딪친다** — 위 §6 "커밋 직전 fetch"로 막는다(§12 10-04: nexa-ui를 nexa-dir3 세션과 함께 씀).
- 협업 세션 하나가 여러 개발 세션을 지원하면 **요청마다 어느 개발 세션 것인지 밝히고**, `target/` 빌드는 한 번에 하나만 돌린다.

## 11. 상시 학습·갱신

운영 기준은 고정이 아니다. 두 세션이 일하다가 **상충(또는 상충할 뻔한 일)** 을 만나면 그때마다 기록하고 규칙을 고친다.

- **상충의 범위**: 같은 파일을 양쪽이 고침 · 한쪽이 고치는 중에 다른 쪽이 빌드/재시작/포맷 · 서로 다른 결론을 문서와 코드에 각각 적음 · 같은 일을 둘이 중복 수행 · 지시가 엇갈림(사용자 지시 ↔ 상대 세션 요청) · 메시지를 못 읽어 낡은 전제로 진행 · 띄운 프로세스/격리 폴더/포트가 겹침 · git 작업 트리 상태를 한쪽이 바꿈.
- **절차**:
  1. 알아챈 세션이 즉시 멈추고 상대에게 **상충 통지**(§4-3)를 보낸다.
  2. 수습 방법은 **개발 세션이 정한다**(기본 = §3 파일 소유 · 사용자 지시 우선 · 나중 지시 우선).
  3. 개발 세션이 **재발 방지 규칙 한 줄**을 정해 보낸다.
  4. 협업 세션이 §12 원장에 한 행을 더하고, 규칙이 바뀌면 이 문서 본문과 [CLAUDE.md §3](../CLAUDE.md) 요약을 함께 고친다.
  5. 그날 journal에 한 줄.
- 상충이 없었어도 **잘 통한 방식**(위임 형식 · 회신 형식 · 작업 순서)은 원장에 "굳힘"으로 적는다. **효과 없던 규칙은 지운다**(쌓기만 하지 않는다).
- **점검 시점**: 사용자가 "commit · main 병합 · push"를 요청할 때마다 협업 세션이 그 세션 동안의 통지를 훑어 원장에 빠진 것이 없는지 보고, 없으면 "운영 기준 변경 없음" 한 줄을 회신한다.
- 협업 세션도 스스로 발견한 개선안을 제안할 수 있다(제안 → 개발 세션 확정 → 기록). 출처는 "사용자"(사용자가 직접 정함)와 "세션 제안"(세션이 정함)으로 구분한다.
