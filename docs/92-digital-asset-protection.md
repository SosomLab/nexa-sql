# 92. 디지털 자산 보호 설계 — 무엇을 · 무엇으로부터 · 어느 층에서 지키는가(**설계만** · 사용자 09-27 "로컬 기준정보 기반 생성 + 클라이언트 분석 지연 기법" 접수 → 범위 합의용)

> 근거: [23 §2-3 신뢰 경계](23-license-activation.md) · [25 §4 사내 인증 서버 · §11 장치/사용자 인증 · §12 발급기 · §13 차별점](25-license-tiers-and-server.md) · [91 루트 키 운영](91-license-root-key-operations.md) · [21 §7 세션 자격 금고](21-connection-profiles.md) · [33 배포·서명](33-distribution-and-packaging.md).
> 원칙 상위: **DR-1 단순성 · 사용자 신뢰**(난독화·안티디버깅 없음 · 23 §2-3) · **네트워크 규칙 26 §8**(전화홈 0 · 폐쇄망 우선). 이 문서는 그 원칙 안에서 "할 수 있는 것 · 하지 않을 것 · 결정이 필요한 것"을 가른다.

## 0. 결론 먼저

1. **지켜야 할 비밀은 하나 — 루트 비밀키**(91 §0). 앱 바이너리 · 라이선스 파일 · 발급기 코드 · 형식은 공개돼도 안전이 무너지지 않는다.
2. **강한 보호는 서버 검증에 둔다**(25 §4 리스 · 좌석 · 하트비트). 로컬 판정은 "정직한 고객이 쉽게 · 우회는 귀찮게"(23 §2-3)까지만 — 단일 네이티브 바이너리의 공개키 교체·분기 패치는 **어떤 로컬 기법으로도 막지 못한다**.
3. **클라이언트 분석 지연 기법은 효과 대비 비용이 크고 DR-1과 충돌**한다(§3 표). 권장 = 이미 켜져 있는 것(`strip = "symbols"` · `lto = "fat"` · `panic = "abort"`)만 유지하고 난독화·안티디버깅·자기 무결성 검사는 **도입하지 않는다**. 대신 저비용·무해한 보강 넷(§2-3)을 권장안으로 낸다.
4. 결정이 필요한 것은 **범위 넷**(§5 D-227~D-230)뿐이다. 코드 작업은 확정 뒤 T-243으로.

### 1-2. 공격자(무엇으로부터) — 현실적인 넷

| 유형 | 동기 · 능력 | 우리가 막을 수 있는가 | 대응 층 |
|---|---|---|---|
| ① **정직한 사용자의 실수** | 다른 PC에 복사 · OS 재설치 · 파일 분실 | ✅ 안내와 셀프 서비스로 | 23 §1-4 판정 메시지 · T-46 백업/복원 · 재발급(L-6) |
| ② **가벼운 공유**(파일을 동료에게) | 기술 0 | ✅ 기기 ID · 기기 열거 5대 | A3 · 25 §11-2 |
| ③ **크래커**(바이너리 패치 · 키 교체 · 크랙 배포) | 디스어셈블러 · 시간 | ❌ 로컬로는 불가 — **귀찮게**만 | §2-3 보강 · 서버 검증(Org) · 법(DR-2) |
| ④ **내부자·발급 PC 침해**(루트 키 유출) | 물리 접근 · 악성코드 | ✅ 봉투 + 오프라인 보관 + 회전 | 91 §3~§6 |

## 2. 보호 층(어느 층에서)

### 2-1. 암호학 층(있음 · nexa-license) — 위조·변조 방지

- 서명 대상 = `Doc::canonical`(정렬 · LF · `sig` 제외 · 도메인 `nexa/license/v1`) → 키 순서·주석·CRLF를 바꿔도 같은 본문 · 값 하나만 바꿔도 다른 본문(시험 `value_change_changes_canonical`).
- 기기 ID = SHA-256(`nexa/machine-v1` ‖ OS 기기 원문)[..20] — 원문(MachineGuid 등)을 파일·대장에 남기지 않는다(시험 `domain_separated`).
- 판정 = `verify::verify_license`(서명 → product → machine → 시각) · 앱과 발급기가 **같은 코드**로 자기 검증(25 §12-3 `verify`).
- 키 회전 = `ROOT_KEYS` 여러 개 동시 내장(V1·V2) — 유출 시 새 키 발급분을 옛 앱도 받게(D-27 · 91 §5).

### 2-2. 서버 층(설계 있음 · 25 §4) — Org 티어의 실제 집행

- 리스 TTL(기본 7일) + 하트비트 10분 + 좌석 회수 → 크랙된 바이너리도 **좌석·감사 로그·중앙 프로필 배포**(25 §13-4)는 얻지 못한다. 기업이 사는 것은 기능이 아니라 이 운영 기능이므로(25 §13-1 ③) ③의 이득이 작다.
- 선택적 온라인 발급 자동화(2차 · D-29)는 **강제 확인이 아니다** — 폐쇄망 우선·전화홈 0(26 §8)을 지킨다.

### 2-3. 로컬 보강 넷(권장안 · 저비용 · DR-1과 충돌 없음)

| # | 보강 | 효과 | 비용 | 비고 |
|---|---|---|---|---|
| R1 | **판정 지점 분산** — `check(Feature)`를 게이트 위치 규칙(23 §4-2)대로 UI가 아니라 Core/Runner 입구에 두고, 상태를 `LicenseState` 한 값으로 캐시하되 **재판정 트리거**(파일 mtime · 기동 · 12h nudge 시점)마다 다시 계산 | 분기 하나 뒤집기로 전부 열리지 않음(패치 지점 N개) | 소 — 설계대로 배선하면 자연히 | 이미 23 §4-2 |
| R2 | **시각 기준 = 빌드일**(`NSQL_BUILD_DATE` · 23 §1-4) | 시계 되돌리기 무효(영구 모델) | 소 — `build.rs` 한 줄 | 미구현(T-32') |
| R3 | **공개키 2개 이상 상시 내장 + 형식 판 두 개 검증**(`nxl1`·`nxl2` · D-48) | 회전·개편 때 옛 앱이 남지 않음 → 크랙 판이 오래 살아남는 이득 감소 | 소 | 25 §12-2 |
| R4 | **라이선스 파일 위치 고정 + 원자적 쓰기**(`fs` feature · 사용자 폴더 → 기기 공용 → 리스 순 · 25 §11-2) | 임의 위치 파일로 판정을 흔들 수 없음 · 백업/복원(T-46) 단순 | 소 | nexa-license `fs` ☐ |

이 넷은 "정직한 고객이 쉽게"를 해치지 않고 ③의 비용을 조금 올린다. **넷 다 새 의존·새 스레드·네트워크 0**(39 §3 부하원 등재 불필요).

## 3. 클라이언트 분석 지연 기법 — 효과 검토(사용자 09-27 질문의 답)

| 기법 | 막는 것 | 실제 효과(단일 네이티브 바이너리 기준) | 비용·부작용 | DR-1 충돌 | 판정 |
|---|---|---|---|---|---|
| 심볼 제거 · LTO · panic=abort | 함수 이름으로 판정 지점 찾기 | 낮음~중(이름 없이도 문자열·호출 그래프로 찾는다) | 0 — **이미 켜져 있음**(`[profile.release]`) | 없음 | ✅ 유지 |
| 문자열 암호화(오류 문구 · 키 상수) | 문자열 검색으로 지점 찾기 | 낮음(복호 지점이 곧 표식) | i18n `Msg` 전체가 대상 · 진단·로그 가독성 저하 | 있음(단순성) | ❌ |
| 제어 흐름 난독화(도구 · 매크로) | 디스어셈블 가독 | 중(시간을 늘림) — 그러나 공개키 상수 교체는 그대로 가능 | 빌드 재현성 · 성능(26 §7 회귀) · 3-OS 툴체인 | **직접 충돌**(23 §2-3 "하지 않는다") | ❌ |
| 안티디버깅(ptrace · IsDebuggerPresent · 타이밍) | 동적 분석 | 낮음(패치로 제거) · 오탐 = 정직한 사용자·개발자 피해 | 보안 소프트 오탐 · 디버깅 불가 | 직접 충돌 | ❌ |
| 바이너리 자기 무결성 검사(자기 해시 · 서명 확인) | 패치된 바이너리 실행 | 낮음(검사 자체를 패치) · **코드 서명 부재 시 기준 해시를 어디에 두나**의 순환 | 자체 갱신·포터블·개발 빌드 전부 예외 처리 | 있음 | ❌(코드 서명 DR-20이 먼저) |
| 공개키를 여러 조각·연산으로 조립 | 상수 교체 | 낮음(조립 결과를 덮으면 끝) | 가독성 저하 · 시험 어려움 | 있음 | ❌ |
| 서버 측 검증(리스 · 하트비트 · 좌석) | 크랙 판의 **조직 기능** 사용 | **높음** — 우회하려면 서버까지 위조해야 하고 감사 로그에 남는다 | 25 §4(설계 완료 · 구현 미착수) | 없음 | ✅ 이것이 본진 |
| OS 코드 서명·공증(DR-20) | 변조 바이너리 실행 경고(Gatekeeper · SmartScreen) | 중(사용자에게 "변조됨"을 보이게) — 우회는 가능하나 배포 신뢰의 기준선 | 인증서 비용 · 파이프라인 자리는 있음(33) | 없음 | ⏸ 별도 요청 시 |

결론: **"분석 지연"은 하지 않는다**(효과 낮음 · DR-1 충돌 · 정직한 사용자 피해). 이득이 있는 것은 이미 켜진 `strip/lto` · 서버 검증 · 코드 서명뿐이며 셋 다 이 문서 밖에서 결정돼 있다(profile · 25 §4 · DR-20).

## 4. 사용자 자산(A6) — 라이선스보다 먼저

라이선스 우회는 SosomLab의 손실이지만 **접속 비밀번호 유출은 사용자의 손실**이다. 보호 우선순위는 A6 > A1 > 나머지. 현재 ✅ = DR-22 볼트(DPAPI/Keychain/0600) · 21 §7 세션 금고(메모리만 · 종료 시 소멸) · CLI `--password-stdin` · 로그·트랜잭션 로그·대장에 비밀번호 0. 남은 점검 = 라이선스 층(T-32')이 새 로그를 만들 때 `licensee`·이메일·기기 ID 원문을 **로그에 쓰지 않는다**(대장과 같은 접두 규칙) — T-243 체크리스트에 포함.
