## 0. 한 줄 결론

**"테이블 편집"은 구조(DDL) 편집기다** — 데이터 편집(87)과 다른 기능이다. 권장안 = **편집기 자리의 뷰 탭**(모달 아님) · 변경은 **묶음(ChangeSet) → 방언별 DDL 생성 → 미리보기(편집 가능) → 백업(114) → 문지기 실행 → 탐색기·메타 즉시 갱신** 한 길 · 즉시 적용 없음 · 테이블 재생성(drop-recreate) 금지(SQLite만 공식 12단계 재생성) · 구현 = **의존 0 순수 크레이트 `nsql-ddl`**(모델·차이·DDL 렌더러·골든 시험) + 앱 모듈(지연 생성) · 격리 = **내장 모듈 + 지연 생성 + 결과 타입 오류 경계**(별도 프로세스·WASM은 비용 대비 효과 없음 · §5-3) · 영향 = 기동 0 · 열 때 1 왕복(상세 캐시 재사용) · 용량 +0.3~0.6 MB · 메모리 = 열린 탭만(§6).

### 2-1. 협업 검증 결과(공식 문서 기준 · [119a](119a-table-editor-survey.md) §A~§D)

- 7종 전부 "변경 묶음 → 한 번에 적용 + DDL 미리보기". **미리보기를 직접 고치게 하는 것은 DataGrip뿐**(pgAdmin·SQL Developer = 폼이 단일 원천 · 미리보기 읽기 전용) → D-317의 "편집 가능"은 소수 방식이다(§7 권장안 유지 · 이유 = 이 제품은 SQL Preview 부품이 이미 편집 가능 · 파서 검증 1회).
- **재생성 위험을 기본 차단하는 것은 SSMS 옵션뿐**("Prevent saving changes that require table re-creation" · 기본 켬 · 대상 5 = 중간 컬럼 추가 · 컬럼 삭제 · NULL 허용 변경 · 순서 변경 · 타입 변경 · MS 권고 = 끄지 말고 ALTER) · Toad = Rebuild Table 마법사로 **분리** · 나머지 = ALTER만(⚠). → D-318(재생성 금지 · SQLite만 분리된 선택 기능)과 같은 방향.
- **서버 반영 뒤 undo는 어느 도구에도 없다**(Revert/Reset = 미저장 버리기) · 트랜잭션 묶음·자동 롤백을 문서로 보장하는 도구 = 확인 못 함 → D-321(중단 + 백업 안내)이 업계 관례 이상.
- 확인 못 한 항목(119a §C) = DataGrip 트리거/파티션·USING·트랜잭션 · DBeaver Persist 창 복사 여부 · Toad 탭 목록(포럼 근거) · SSMS 재생성 내부 절차 · TablePlus 인덱스/FK/코멘트 · pgAdmin ALTER 차분 표시 · SQL Developer 데스크톱 문서 404 → 설계에 영향 없음(전부 2단계 이후 항목).

## 3. 제공 기능(권장안)

### 3-1. 재사용 자산(이 저장소에 이미 있는 것 · 대조 = 협업 초안)

| 자산 | 어디 | 구조 편집에서의 쓰임 |
|---|---|---|

| 그리드 편집 부품 nexa-ctl `gridedit` + `ChangeSet` + `SqlGen` + `Runner::apply_changes`(87) | nexa-ui · nsql-run | **컬럼 그리드의 인라인 편집 UX**(Enter/Esc · Tab · 붙여넣기) · "변경 묶음 → 문장 → 적용" 흐름의 본보기(3겹 보호는 DML용 · DDL은 §3-4) |

| DDL 뒤 탐색기 갱신(57) · 테이블 노드 새로 고침 = 그 테이블 메타 즉시 재조회(134차 10-21) | nexa-sql | 적용 뒤 **그 테이블만** 갱신 |

| 식별자 인용 `identq` · 별칭 · 방언 `Caps` | nsql-core · nsql-run | 생성 DDL의 인용 · 능력 판정 |

**3-1-a. 새로 만들어야 하는 것(협업 코드 탐색 · [119a](119a-table-editor-survey.md) §3-1)** — ① **차이 → ALTER 생성 엔진 없음**(gen.rs는 CREATE 조각만) = `nsql-ddl`의 핵심 ② `apply_changes` 3겹 보호는 DML 전제(영향 행 = 1)라 **DDL 적용기는 새로**(백업 게이트는 `run_text_in` 경로에 있으니 편집기 적용도 그 길을 탄다) ③ `ColumnInfo.data_type`이 문자열 하나(길이·정밀도·스케일 미분리) → `nsql-ddl::ColumnType`이 방언별로 **파싱·렌더**(골든 시험) ④ identity · collation · CHECK 식 · FK 동작(ON DELETE/UPDATE) · 인덱스 옵션은 카탈로그 읽기에 없음 → 1단계 = 키·인덱스·코멘트 읽기 범위에서 시작 · 나머지 = 2단계 읽기 확장 ⑤ **MySQL 전용 드라이버 없음**(`Dialect::Mysql`만) → MySQL 렌더러는 골든 시험만 · 실서버 E2E = Oracle·PG·SQL Server·SQLite 4방언.

### 3-3. 방언 능력표(초안 · 코드 = `Caps` 확장)

| 연산 | Oracle | PostgreSQL | SQL Server | MySQL | SQLite |
|---|---|---|---|---|---|
| 컬럼 추가/삭제 | ✓ / ✓ | ✓ / ✓ | ✓ / ✓ | ✓ / ✓ | ✓ / ✓(3.35+) |
| 이름 바꾸기(컬럼) | ✓ | ✓ | `sp_rename` | ✓(8.0 RENAME COLUMN) | ✓(3.25+) |
| 타입 변경 | `MODIFY` | `ALTER TYPE [USING]` | `ALTER COLUMN` | `MODIFY` | ✗ → **재생성** |
| NULL/기본값 | ✓ | ✓ | ✓(기본값 = 제약) | ✓ | ✗ → 재생성 |
| 컬럼 순서 | ✗ | ✗ | ✗ | `AFTER` | ✗ → 재생성 |
| 제약 추가/삭제 | ✓ | ✓ | ✓ | ✓ | ✗ → 재생성(FK 일부 ✓) |
| 인덱스 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 코멘트 | `COMMENT ON` | `COMMENT ON` | `sp_addextendedproperty` | `ALTER … COMMENT` | ✗(없음) |
| 트랜잭션 DDL | ✗ | ✓ | ✓ | ✗ | ✓ |

✗ → 재생성 = SQLite 공식 12단계(`PRAGMA foreign_keys=OFF` · 새 테이블 · 복사 · 삭제 · 이름 바꾸기 · 인덱스/트리거 재생성 · `PRAGMA foreign_key_check`)만 **선택 기능**(D-320)으로 제공 · 그 밖 DBMS는 재생성 **하지 않는다**(SSMS의 drop-recreate 금지 = 데이터 보호 불변식의 DDL 판).

### 3-4. 데이터 보호(87 §14의 DDL 판 · 불변식)

1. **미리보기 없이 적용 없음** — 사용자가 본 스크립트가 곧 실행되는 스크립트(편집했으면 편집본 · 구문 검증은 방언 파서로 1회).
2. **재생성 금지** — 데이터가 다른 테이블로 옮겨지는 경로는 SQLite 선택 기능뿐 · 그때도 백업 + 행 수 대조(복사 전/후 `COUNT(*)` 같음) + 실패 = 원본 그대로.
3. **적용 전 객체 백업 = 늘**(114 §7-2 부품 재사용 · `backups/objects/<프로필>_<스키마>.<객체>_<종류>.<시각>` + 실행 스크립트 `…_applied.sql` · 새 테이블 = 백업 대상 없음 → 생성 스크립트만 보관) · 백업 실패 = 운영 **막음** · 비운영 = 사유 + [취소]/[백업 없이 계속](기본 취소 · 설정 `tbledit.backup_fail` ask/deny).
4. **적용 직전 서버 재확인**(F-13) — 원본과 다르면 중단.
5. **위험 변경 사전 검사**(F-12) — 경고 없이 열 삭제·축소 금지.
6. **운영기 = 같은 가드**(F-16) — 2단 확인 · 백업 필수(실패 = 막음) · 검사 끌 수 없음 · deny 설정 · 보류 중 금지(사용자 확정 10-21).

### 5-2. 지연 생성(최초 실행 영향 0)

- 탭을 처음 열 때 모듈 상태를 만든다(`Option<TableEditor>`) · 정적 표·전역 초기화 없음 · 설정 키는 레지스트리 상수만(모든 키와 같음 · 비용 0).
- 상세 읽기는 L3 캐시(85)가 있으면 왕복 0 · 없으면 1회(실측 Oracle 1.3 s → 백그라운드 세션 · 탭은 "읽는 중" 뒤 채움 · T-374 방식).
- **회수 = 0으로**(★ 사용자 확정 10-21 "지연 생성 후 사용하지 않으면 종료 즉시 + 주기적 미사용 로직으로 0으로 회수"):
  1. **탭 닫기 = 즉시 전부 해제** — 모델 · 그리드 · 미리보기 문자열 · 위험 검사 결과 · 백그라운드 요청 취소(LatestIntent 99) · 스레드 0(백그라운드 메타 세션은 공용이라 남지 않음).
  2. **열려 있어도 미사용이면 주기 회수** — 마지막 입력·표시 뒤 `tbledit.idle_secs`(기본 300 · 0 = 끔)가 지나면 **재생성 가능한 것**(그리드 행 캐시 · 미리보기 문자열 · 타입 완성 목록 · 상세 사본)을 비우고 모델(편집 내용)만 남긴다 → 다시 활성화되면 즉시 재생성(왕복 0 · 모델에서).
  3. **마지막 탭이 닫히면 모듈 상태 자체 해제**(`Option<TableEditor>` → None) + 다음 유휴 회수 주기(`memtrim` 82차 · `mem.trim` 훅)에 할당자 반납 → 메모리 원장 `Cat::TableEdit` **0** · 캐시·스레드·타이머 0 = 열기 전과 같음.
  4. 등재 = 39 §3 부하원 원장(스위치 `tbledit.enabled` · 상한 `tbledit.max_tabs` · 주기 `tbledit.idle_secs`) · 71 §C-2 회수 시험 **R7 = 열기 → 편집 → 닫기 → 60 s 뒤 `mem.dump` Cat::TableEdit 0 · 전용 WS 복귀** · `mem.dump` 줄 `tbledit=<탭 수>/<바이트>`.

### 5-4. 오류의 **완전한** 분리(★ 사용자 확정 10-21 "메인 편집기에 영향이 없도록")

사실 = 이 저장소의 Release 프로필은 `panic = "abort"`(Cargo.toml) → 프로세스 안 어떤 패닉도 앱 전체를 끝낸다(기존 `catch_unwind`(탐색기 메타 스레드)는 Debug에서만 효과). "영향 0"을 **보장**하려면 둘 중 하나가 필요하다.

## 9. 열린 질문(사용자)

1. 탭(권장) vs 모달 중 어느 쪽에 익숙한가(Toad 사용자는 모달에 익숙).
2. 새 테이블 생성을 1단계에 넣을지(권장 = 넣음 · 같은 모델).
3. 컬럼 순서 이동을 MySQL 외에서 "재생성 필요"로 비활성할지, 아예 숨길지.
4. 미리보기 편집본을 그대로 실행할지(권장 = 그대로 · 파서 검증 1회) vs 편집하면 "편집기로 보내기"만 허용할지.
5. 라이선스 안내 모달 빈도 = 앱 실행마다 첫 열기 1회(권장) vs 탭을 열 때마다(D-328 비고).

**적용** = [Apply…] → 메타 세션이 구조를 다시 읽고 위험 검사 `COUNT`를 돌림 → 연 뒤 서버 구조가 달라졌으면 중단(F-13) → 미리보기 창(머리 주석 = 문장 수 · `PRODUCTION` · `DANGER`/`WARNING` · 0이 아닌 검사 결과 · `NOT APPLIED`) → 창의 [Apply] → **문장 하나씩**(`gate_open` · 운영 확인 깃발 · 객체 백업은 첫 문장 앞에서 한 번) → 오류면 그 자리에서 멈춤 + "Stopped after n of m"(자동 되돌리기 없음 · D-565) → 구조 다시 읽기(성공 = 편집 초기화 · 실패 = 남은 편집 유지 `rebase`).

### 10-2. 1차의 제약

- 테이블 재생성 없음(D-318) — 재생성이 필요한 변경은 적용하지 않고 경고 줄에 적는다.
- 컬럼 순서 이동 = MySQL/MariaDB만 문장으로 된다(그 밖 = 막힘).
- SQLite = 타입 · NULL · 기본값 · 제약 변경 막힘(추가 · 이름 바꾸기는 됨) · 코멘트 미지원.
- 서버에서 읽은 FK · CHECK = 1차 ~ 3차는 이름 바꾸기 · 삭제만(읽지 않은 속성 보호 · D-563) → **4차부터** 규칙 · 식을 읽은 방언(Oracle · PostgreSQL · SQL Server · MySQL)의 **잠기지 않은** 제약은 컬럼 · 정의 편집 가능(`DROP` → `ADD`) · 잠긴 제약(지연 검사 · 비활성 · 미검증 등)과 속성을 못 읽은 방언 = 종전대로 이름 바꾸기 · 삭제만(§10-7).
- PK/UK와 같은 이름의 인덱스는 인덱스 목록에서 숨긴다(키 섹션에만).
- 새 이름 = 방언 접힘 · 행 추가 = 맨 끝(D-564) — 11-28부터 둘 다 설정(`tbledit.fold_names` · `tbledit.add_row` · 기본 = 그대로 · D-571 · §10-8).

**첫 검증의 발견과 처리(같은 날 수정 · 위 표 = 수정 뒤)**

1. **SQL Server 기본값 변경** — 기존 기본값 제약을 지우는 문장이 `EXEC( )` 안의 `QUOTENAME` 호출 때문에 거절됐다 → 문장을 변수에 먼저 만들어 실행하는 꼴(`DECLARE @nsql_sql nvarchar(max) = N'… DROP CONSTRAINT ' + QUOTENAME(@nsql_df); IF @nsql_sql IS NOT NULL EXEC(@nsql_sql)`)로 **고침** · 뒤 문장(새 기본값 · 확장 속성 추가/갱신)까지 실서버 확인.
2. **중단 문구가 상태줄에서 덮였다**(3방언 · 실행 요약 `1 error(s)`) → 마무리 안내를 완료 처리의 맨 끝에서 쓰게 **고침**.
3. **PostgreSQL 실패 뒤 가짜 변경**(입력 `varchar(20)` ↔ 서버 표기 `character varying(20)` → `ALTER COLUMN … TYPE` 대기 문장) → 타입 표기 정규화(`norm_type`)로 **문장은 사라짐** · 줄 표식만 남음(재검증 뒤 수정 2).
4. **Oracle 기본값을 읽지 못했다**(칸 빈 글) → `all_tab_columns.data_default`를 한 번 더 읽어 **고침**.
5. 미리보기 창이 열린 뒤 상태줄 글 잔류 → `Apply changes - <테이블>`로 **고침**.

**재검증 뒤 수정(11-27 · 겉보기 2건 · 개발 확인 = fmt · clippy · `nexa-sql tbledit` 9 / 0 · `nsql-catalog` 35 / 0 · Debug 빌드 · V1 `tbledit` 15 / 0 — 실서버 재확인은 다음 실기)**

1. Oracle — 기본값을 지우면 서버 카탈로그가 `NULL`을 돌려줘 칸에 글자 `NULL`이 보였다 → `table_edit_load`가 `data_default`의 글자 `NULL`(대소문자 무시)을 빈 글(= 기본값 없음)로 읽는다.
2. PostgreSQL — 실패 뒤 다시 읽은 줄 가운데 타입 표기만 다른 줄(`varchar(20)` ↔ `character varying(20)`)에 표식 `*`가 남았다 → 줄 표식(`row_mark`)도 타입을 `norm_type`으로 견준다(문장 생성과 같은 잣대 · 칸 글이 사용자가 친 표기로 남는 것은 의도 = 편집 보존).

**남은 것**

1. 구조 편집 탭에서도 상태줄에 `Read-only` 칸.
2. SQL Server는 인덱스가 걸린 컬럼의 NULL → NOT NULL을 서버가 막는다(지금은 Warn으로만 나감 · 사전 경고 없음).
3. 미리보기 창의 제목 지정 캡처는 Linux에서 실패(T-524 · 창 열림은 창 수로 판정).

**확인하지 않은 것** = (재검증 뒤 수정 2건의 실서버 판 = §10-5에서 확인) · MySQL/MariaDB 실서버(프로필 없음) · 운영 프로필 경로(2단 확인 · `tbledit.prod=deny`) · 미리보기 창의 [Apply] 버튼(창 열림까지만 · 적용은 `tbledit.apply_now`로 같은 길을 탐) · Windows · macOS 실기 · 71 영향 측정(§6 표).

**④의 경위(데이터 보호)** — `rebase`(적용이 중간에 멈춘 뒤 · 고친 스크립트를 실행한 뒤 구조를 다시 읽어 남은 편집을 지키는 길)는 지금까지 편집 모델의 항목에 새 원본의 이름을 맞춰 줄 뿐, **서버에 새로 생긴 컬럼 · 제약 · 인덱스(지난 원본에 없고 편집 모델도 모르는 것)를 편집 모델에 들이지 않았다.** 그러면 다음 차이 계산이 그것을 "원본에는 있고 편집 모델에는 없는 항목 = 지울 것"으로 잡아 `DROP COLUMN`(위험 등급 Danger) 문장을 만든다. 발견 = ②를 V1로 돌리다가(고친 스크립트로 `extra2`를 더한 뒤의 덤프에 `stmt|Danger|ALTER TABLE … DROP COLUMN extra2`). 수정 = 그런 항목을 `origin = 자기 이름`으로 편집 모델 끝에 들인다 + 시험 `rebase_adopts_server_side_additions_and_keeps_pending_edits`. 사용자가 탭에서 지운 항목(지난 원본에 있던 것)은 종전대로 "지울 것"으로 남는다.

1차 · 2차 커밋판(e32337bf · e7e4d719)에도 있던 결함이다. 그때 `rebase`로 들어가는 길은 "문장이 중간에 멈춘 뒤"뿐이라, 서버 쪽 추가분이 생기는 경우는 **다른 세션이 같은 테이블에 컬럼 · 제약 · 인덱스를 더한 뒤 이 탭의 적용이 중간에 멈춘 때**뿐이었다. 그 경우에도 다음 [Apply…]는 방금 다시 읽은 원본을 기준으로 하므로 적용 직전 재확인(F-13)을 통과한다 — 미리보기에 위험 문장으로 보이기는 하지만 사용자가 요청하지 않은 삭제가 스크립트에 들어가는 것이라 데이터 보호 결함으로 적는다(실제로 일어났다는 보고는 없다).

**설계와 다른 점** — F-15의 줄 버튼([열기] [편집기로] [비교]) 대신 더블클릭 / Enter = 편집기 탭으로 열기 하나 · 칸 = 시각 · 결과(문장 수 포함) · 파일. §9 질문 4 권장안의 "파서 검증 1회"는 문장 분리까지다(고친 글의 문법 · 위험은 다시 검사하지 않는다 = 사용자가 쓴 SQL · D-568).

**판정 명령(시험 전용)** = `tbledit.undo` · `tbledit.redo` · `tbledit.apply_script:<파일>`(파일의 글 = 미리보기에서 고친 글 · 창의 [Apply]와 같은 함수로 들어간다 · 미리보기 창과 그 앞의 재확인은 거치지 않는다) · `tbledit.section:history` · 덤프 = `hist|<되돌릴 수>|<다시 실행할 수>` 줄(둘 다 0이면 없음).

| ④ | 다른 스키마의 참조 대상 | 참조 테이블이 다른 스키마면 `스키마.테이블`로 읽어 `ADD CONSTRAINT … REFERENCES 스키마.테이블`이 되게(PostgreSQL = `rn.nspname \|\| '.' \|\| rt.relname` · SQL Server = `OBJECT_SCHEMA_NAME` · MySQL = `unique_constraint_schema` · Oracle = `table_detail`의 `소유자.테이블`) · 같은 스키마 = 이름만 |
| ⑤ | 재생성 주의 문구(D-570) | 미리보기 머리 주석 — 문장에 `DROP CONSTRAINT` / `DROP FOREIGN KEY` / `DROP CHECK` / `DROP PRIMARY KEY`가 있으면 `-- NOTE: a changed constraint is dropped and then added again. **속성 유실의 경위(데이터 보호 · 있는 그대로)** — 4차의 첫 판은 "삭제 규칙 · 식을 읽었으면 그 테이블의 FK · CHECK 전부 편집 가능"(테이블 단위 `keys_complete`)이었다. 요청받은 판정(a ~ e)은 다 통과했지만, 협업이 판정을 하나 더 얹어 **편집기가 읽지 않는 속성을 붙인 제약**을 고쳐 봤다(임시 자식 테이블 · FK 정의 `CASCADE` → `SET NULL` + CHECK 식 → `qty >= 1` · `Applied 4 of 4`):

| 방언 | 처음(카탈로그) | 첫 판에서 적용한 뒤 |
|---|---|---|
| PostgreSQL | FK `ON UPDATE CASCADE ON DELETE CASCADE DEFERRABLE INITIALLY DEFERRED` · CHECK `NOT VALID` | FK `ON DELETE SET NULL`뿐(갱신 규칙 · 지연 검사 사라짐) · CHECK 검증된 상태로 |
| Oracle | FK `DEFERRABLE` · `DEFERRED` · CHECK `DISABLED` · `NOT VALIDATED` | FK `NOT DEFERRABLE` · `IMMEDIATE` · CHECK `ENABLED` · `VALIDATED` |
| SQL Server | FK 갱신 규칙 `CASCADE` · CHECK `is_disabled = 1` · `is_not_trusted = 1` | FK 갱신 규칙 `NO_ACTION` · CHECK `0` · `0` |

키 섹션에는 세 방언 모두 `<부모>(id) ON DELETE CASCADE`만 보였고 경고도 없었다 = D-563이 막으려던 **조용한 구조 훼손** 그대로. 비활성 CHECK는 다시 만들 때 기존 행을 검증하므로, 위반 행이 있으면 "`DROP` 성공 · `ADD` 실패 → 제약 유실"로도 이어진다. 커밋 전에 개발이 고쳤다 = 갱신 규칙을 함께 읽어 정의에 싣고(②), 다시 적어 줄 수 없는 속성이 있는 제약은 제약 단위로 잠근다(③). 첫 판은 커밋되지 않았다.

**실패 유도에서 본 것(중단 길의 실제 모습 · 3방언 같음 · ⑤의 근거)** — FK의 참조를 부모의 UNIQUE 컬럼으로 바꿔(기존 행이 위반) `DROP` 성공 · `ADD` 실패를 만들었다: 상태줄 `Stopped after 1 of 2 statement(s) - the rest was not applied. Nothing is rolled back automatically; see the object backup.` · **서버에서 FK가 실제로 사라진다** · 화면 = `dirty=true` · FK 줄 표식 `+` · 남은 문장 = `ADD CONSTRAINT` 하나(두 번째 `DROP` 없음) · 기록 = `Stopped after 1 of 2` · `_applied.sql` = `applied 1 of 2` + `-- STOPPED:` + 두 문장 · 객체 백업(첫 문장 앞)에 원래 FK가 있다 · 같은 탭에서 정의를 고쳐 다시 적용 = 문장 1(`ADD`만) → `Applied 1 of 1` · 카탈로그에 FK 복귀. 서버 오류 원문 = PostgreSQL `23503: insert or update on table "<T>" violates foreign key constraint "<T>_fk"` · Oracle `ORA-02298`(부모 키 없음) · SQL Server "ALTER TABLE 문이 FOREIGN KEY 제약 조건 … 과(와) 충돌했습니다".

**소견(4차 · 남긴 것)** — ① SQL Server 객체 백업 DDL의 FK에 `ON DELETE`가 없다(`… REFERENCES dbo.<부모> ([id]);` · 실제는 `SET NULL`) — PostgreSQL · Oracle 백업은 규칙이 들어 있다 → **T-526** ✅ 11-28(journal 11-28 §3) ② 잠긴 줄에 이유 표시가 없다 → ✅ 11-28 안내 줄(아래 덧붙임 · 속성별 구분은 §10-3 9) ③ 같은 스키마의 참조 대상은 스키마 한정 없이 `REFERENCES <부모> (id)`로 나간다(PostgreSQL = 검색 경로 · SQL Server = 기본 스키마에 기댐 · 다른 스키마 대상만 한정) ④ Oracle의 시스템 이름 제약(`SYS_C…` · 컬럼 `NOT NULL` 포함)은 제약 목록 질의와 속성 질의가 같은 조건(`generated = 'USER NAME'`)으로 걸러 키 섹션에 나오지 않는다 = 편집 대상이 아니다(코드 읽기 · 종전부터).

**확인하지 않은 것(4차)** = 다른 스키마를 참조하는 FK(스키마를 새로 만들어야 해서 실행하지 않음 — 7번째 열이 빈 글인 쪽만 확인) · 다중 컬럼 FK(판정 명령 값에 쉼표를 못 씀) · MySQL / MariaDB 실서버(MariaDB는 `enforced` 열이 없을 수 있다 — 질의가 실패하면 `None` = 이름 바꾸기 · 삭제만으로 떨어지는지 포함) · `MATCH FULL` · `NOT FOR REPLICATION` · 신뢰되지 않은 SQL Server FK의 잠금 · JOIN FK 완성 회귀(PostgreSQL 종류 글자 수정의 소비자) · 잠긴 줄의 화면 표시(흐린 글) · 화면 조작 경로 전부(판정 = 기동 명령) · 고친 판의 전체 시험 · V1 전체 31 · Windows · macOS.
