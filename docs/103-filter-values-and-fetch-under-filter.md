# 103 — 결과 필터의 두 상한: 값 목록(표시 상한) · 필터 중 자동 페치(설계 · 10-07)

> 사용자 10-07 요구 둘. ① "값 목록이 `grid.filter_values_max` 안에서만 검색된다 — 표시용 자료를 따로 만들지 말고 **데이터 원천(RowSource)을 직접** 붙여 검색하면 상한도, 메모리 확장도, 추가 처리도 없을 것" ② "필터를 걸면 받은 행(기본 200)에서 걸러진 행만 남고, 마우스·키보드가 움직일 때마다 200행씩 **1회씩** 더 읽는다 — 속도를 안 깎으면서 계속 읽어야 하나, 필터 중엔 자동 페치를 꺼야 하나, 다른 도구는 어떻게 하나". 둘 다 **속도·메모리를 늘 감안**. 관련 = [77 §2-2](77-data-workbench-architecture.md) 필터 투영 · [43 §3](43-fetch-model-and-result-tabs.md) 페치 모델 · [72 §3](72-size-limits-and-large-file-constraints.md) 상한 원장 · DR-33(한 세트 + 뷰 투영 · 복사 0).

## 0. 한 줄 결론(권장안)

| | 지금 | 권장 |
|---|---|---|
| **A. 값 목록** | 받은 행을 훑어 **문자열 벡터**를 만들며 상한(500)에서 **멈춤** → 그 뒤 값은 검색조차 안 됨("값이 더 있음") | **`DistinctIndex`** = 열마다 *첫 등장 행 번호* `Vec<u32>` + 해시 집합(문자열 복사 0 · 값은 세트 안의 것을 가리킴) · 세그먼트가 올 때 **증분** · 검색은 인덱스 위에서(가져온 행 전부 · 상한 없음) · 표시는 가상화(지금처럼 12행만 그림) · **서버에 더 있으면** 머리에 "가져온 N행 기준" + **[서버에서 값 읽기]**(`SELECT DISTINCT` + 검색어 LIKE 푸시다운 · 상한은 이 길에만) |

## 1. 지금 구조(코드 기준 · 10-07)

- 값 목록(`grid.rs` 값 팝업 열기 · `valuepick.rs`): `distinct_capped((0..rs.len()).map(cell_text), grid.filter_values_max)` — 행을 훑으며 **`Vec<String>`을 만들고** 고유값이 상한+1에 닿으면 **멈춘다**(72 §3 "그 수에서 멈추고 값이 더 있음 표시"). 검색 상자는 그 벡터 안에서만 거른다 → 상한 뒤의 값은 **검색으로도 못 찾는다**(사용자 캡처 = `P`로 시작하는 ITEM_CD가 있는데 목록엔 `08P575`뿐). 종속 목록(`grid.filter_values_scope=others`)도 같은 벡터.
- 메뉴 판 "값 고르기 ▸"(`column_values` · `grid.filter_pick_max` 30)는 빠른 길 — 그대로 둔다.
- 자동 페치(`Grid::clamp`): `auto_fetch && more && !fetching && page_rows > 0 && ((스크롤 끝) || (my == 0 && filters 있음)) && auto_fetch_at != src_rows` → `FetchReq::Next{offset = 원본 행 수, limit = page_rows}`. 필터로 화면이 안 차면(`my == 0`) **매번** 1페이지 — `clamp()`는 마우스 이동·휠·키·그리기마다 돌므로 "사건마다 1회"가 된다. 멈춤 조건이 없어 적중률이 낮으면 **표 끝까지** 읽는다(단지 느리게).
- 서버 쪽 길은 이미 있다: 필터 메뉴 "필터로 서버 재조회"(`filter.requery` = `filter_query()`를 **새 결과 탭**으로) · 조건 바(같은 탭 재조회 · `cond_run`/`cond_run_failed` 되돌림).

## 2. 조사 — 다른 도구(기억 기준 · ✱ = 실기 확인 필요)

| 도구 | 열 필터의 성격 | 값 목록 | 부분 결과 + 필터 |
|---|---|---|---|
| DBeaver | **서버 술어**(결과 패널 Filter = 질의에 WHERE 합성 · 재실행) | "Filter by value" = **받은 행**의 값 + **"Read all values from database"**(`SELECT DISTINCT` · 기본 200 · 검색어가 SQL로) ✱ | 필터 = 재실행이라 페이지는 이미 걸러져 옴 · 로컬만 거르는 모드 없음 |
| DataGrip | **서버 술어**(필터 칸 = WHERE · 페이지 500) · 로컬은 찾기(강조만) | 값 목록 없음(자동완성) | 같음(재실행) |
| TablePlus | 필터 빌더 = **서버 술의**(WHERE) · 페이지 서버 | 없음 | 같음 |
| Toad · PL/SQL Developer · Golden | 그리드 필터 = **재조회**(WHERE) 기본 ✱ | Toad "Filter by value"는 받은 행 ✱ | 같음 |
| SSMS · SQL*Plus | 결과를 **전부** 받는다(페이지 없음) · 필터 없음(정렬만) | — | 해당 없음 |
| Excel | 자료가 **전부 로컬** | 전부 distinct(상한 1만 항목 표시 · 검색은 전체) | 해당 없음 |

공통점: **부분 결과 위의 로컬 필터를 "더 읽어서 채우는" 도구는 없다** — 필터는 서버 술어가 되거나(DB 도구) 자료가 전부 로컬(Excel)이다. 값 목록은 "받은 행 기준 + 서버에서 전부 읽기"의 두 길이 표준(DBeaver).

## 3. 설계 A — 값 목록 = 데이터 원천 직접 참조(T-284)

### 3-1. 자료 구조 — `DistinctIndex`(열마다 · 지연 · 증분)

```
struct DistinctIndex {
    col: usize,
    built_rows: usize,          // 여기까지의 행을 반영했다(세그먼트가 오면 이어서)
    first_row: Vec<u32>,        // 고유값마다 첫 등장 행 번호(값 자체는 세트 안 · 복사 0)
    seen: HashSet<u64>,         // cell_text 해시(충돌은 first_row의 실제 값 비교로 가린다 · 또는 Value 자체 해시)
    nulls: u32,                 // NULL 수(목록엔 (빈 값) 한 줄)
}
```

- **만드는 때** = 팝업을 열 때(그 열만 · 지연 로딩 61 §1-8) · 이미 있으면 `built_rows..rs.len()`만 이어 훑음(세그먼트가 뒤에 와도 **증분**) · 결과가 바뀌면(`set_result`) 버린다.
- **메모리** = 고유값 d개 × (4 B + 8 B) ≈ 12 B/값 · 10만 고유값 = 1.2 MB · 문자열 복사 **0**(표시할 때 `cell_text(rs.cell(first_row[i], col))` — 셀 텍스트 캐시 DR-33 그대로).
- **시간** = 받은 행 n의 한 번 훑기(해시 · 10만 행 ≈ 수 ms) · 예산 `grid.filter_values_budget_ms`(기본 30)를 넘으면 그때까지 만든 것으로 열고 **다음 틱에 이어 만들기**(팝업 머리 "계산 중 N/M…") — 큰 결과에서도 UI가 멈추지 않는다(39 §2).
- **정렬** = 첫 등장 순(지금과 같음) · 정렬 토글(가나다)은 `first_row`를 텍스트로 정렬한 사본 `Vec<u32>`(또 4 B/값).
- **종속 목록**(`values_scope=others`) = 인덱스는 전체로 만들고, 표시할 때 **다른 열 필터를 통과한 행 집합**(`View`의 `row_order` → 비트셋)으로 `first_row`를 거른다(값이 통과 행에 한 번이라도 나오는지 = 세트 안 그 값의 **아무 행**이 통과했는지 → `first_row`만으로는 모자라 **값 → 행 목록**이 필요) → 간단한 방법 = 통과 행만 훑어 **작은 인덱스**를 따로 만든다(통과 행 수 m ≤ n · 필터 바뀔 때마다 · 예산 같음). 기본값이 `others`이므로 이 길이 사실상 기본 — m이 작아 더 싸다.

### 3-2. 검색·표시 — 상한 없음

- 검색 = 인덱스 위 선형 필터(`cell_text` 비교 · 한글 자모 · 대소문자 무시) → 결과 `Vec<u32>` · d ≤ 10만이면 10 ms 안 · 넘으면 예산 분할(위와 같은 "계산 중").
- 표시 = 지금처럼 **가상화**(보이는 `grid.filter_popup_rows` 12행만 그림 · 스크롤 = 인덱스 위치) → 목록 길이와 그리기 비용 무관.
- **상한 `grid.filter_values_max` 폐지**(D-256) — 72 §3 원장에서 "값 목록 = 가져온 행 전부 · 상한 없음(인덱스)"로 바꾸고, 상한은 §3-3 서버 길에만 남긴다(`grid.filter_server_values_max` 1,000). 메뉴 판 `filter_pick_max` 30은 그대로.
- 엑셀식 동작(10-06 3차 = (모두 선택) 3상태 · 검색 결과 선택 · 추가)은 인덱스 위에서 그대로.

### 3-3. 서버에 더 있을 때 — "가져온 행 기준" + [서버에서 값 읽기]

- 결과가 부분(`more == true`)이면 팝업 머리에 **"가져온 N행 기준 · 서버에 더 있음"** 한 줄 + 버튼 **[서버에서 값 읽기]**.
- 누르면 메타 세션이 아니라 **그 탭의 세션**(세션 변수·임시 테이블 의존 · 43 §3-4 규칙)으로 `SELECT DISTINCT q."COL" FROM ( <출처> ) q [WHERE <다른 열 필터 · 조건 바>] ORDER BY 1 FETCH FIRST K ROWS ONLY`(방언 래핑 = 43 §3-4) · `gate_open` · 실행 카드(43 §11) · K = `grid.filter_server_values_max` 1,000 · 결과는 **같은 팝업**이 `RowSource`로 받아(새 구조 없음 · 1열 ResultData) 인덱스를 그 위에 만든다.
- 서버 모드에서 검색어를 치면 **푸시다운**: `WHERE q."COL" LIKE '%P%'`(대소문자 = 방언 `UPPER` · 한글 자모 검색은 로컬 전용) · 디바운스 `intel.delay_ms` 재사용 · 진행 중이면 최신 의도만(99 `LatestIntent`).
- 상한 K에 닿으면 그때만 "값이 더 있음(상한 K · 검색어로 좁히기)".
- 네트워크 규칙(26 §8): 사용자가 누를 때만 · 재시도 없음 · 동시 1건.

### 3-4. 바뀌는 자리

| 자리 | 변경 |
|---|---|
| `grid.rs` 값 팝업 열기 · `column_values` | `distinct_capped(…, filter_values_max)` → `DistinctIndex` 만들기/이어 만들기 · 팝업엔 인덱스(또는 `Arc<ResultData>` + 인덱스)를 넘김 |
| `valuepick.rs` | 값 벡터 대신 인덱스 + `RowSource` 참조로 표시·검색 · 머리 줄(가져온 N행 기준) · [서버에서 값 읽기] · "계산 중" |
| `nsql-core` | (선택) `DistinctIndex` 순수 함수 + 난수 대조 시험(단순 HashSet<String> 모델) — 61 §2 자료 구조 규칙 |

## 4. 설계 B — 필터 중 자동 페치(T-285)

### 4-1. 판정표(순수 함수 + MC/DC)

| 조건 | 동작 |
|---|---|
| 결과 완전(`more == false`) | 로컬 필터 = 정답 · 페치 없음(지금과 같음) |
| 부분 + 필터 추가/변경 + `grid.filter_server=auto` + 번역 가능 | **서버 승격**: `filter_query()`를 **같은 탭**에서 재조회(조건 바 `cond_run`과 같은 길 · 출처 보존 `cond_base`/`prev` · 실패 = 결과 유지 + 테두리/상태줄) → 이후 자동 페치는 걸러진 결과의 보통 페이지 · 칩은 그대로(모델은 술어 목록) · 상태줄 "서버 필터 N행 · 더 있음" |
| 부분 + 번역 불가(정규식 3단계 실패 · IN 1,000 초과) 또는 `filter_server=local` | **채움 상한**: 필터가 바뀐 뒤 자동 페치는 최대 `grid.filter_fill_pages`(3) 페이지 → 멈춤 · 칩 줄/상태줄 배지 "가져온 N행 기준 · [더 가져오기] [전체 가져오기]"(버튼 = 지금 결과 도구줄의 페치/전체 조회 그대로) |
| `filter_server=ask` | 처음 한 번 토스트/모달 "서버에서 걸러 다시 조회할까요? [서버] [가져온 행만] □ 기억" |

- "사건마다 1회"의 뿌리(`my == 0 && filters 있음` → 매번 1페이지)는 **채움 카운터**로 바꾼다: `fill_pages_left`(필터 바뀔 때 = 3 · 페이지가 올 때마다 −1 · 0이면 스크롤 끝에서도 안 읽음 · 사용자가 [더 가져오기]를 누르면 다시 3) — 어떤 모드에서도 **끝까지 자동으로 읽지 않는다**(속도·메모리 · 39 §2).
- 필터를 **지우면** 서버 승격 결과는 출처로 복귀(조건 바의 되돌림과 같은 `prev`) · 조건 바 식과 필터가 함께 있으면 `WHERE 1=1 AND (조건) AND (필터)` 한 문장(합성 한 자리 = `filter_query` + `wrap_condition`).
- 편집 중(`ChangeSet` 있음)엔 서버 승격을 미루고 로컬(채움 상한) — 재조회가 편집 버퍼를 지우기 때문(87 §14 데이터 보호).
- 건수 Σ·행 식별·정렬은 재조회 결과의 보통 규칙.

### 4-2. 왜 "계속 읽기"도 "끄기"도 아닌가

- 계속 읽기 = 적중률 1 %면 200행을 채우려 2만 행을 받는다 — 메모리·WAN 왕복 모두 사용자가 뜻하지 않은 비용(39 §2 · 26 §8 "접속한 적 없는 서버에 지속 트래픽 금지"와 같은 정신).
- 끄기 = "더 있음"인데 안 읽어 사용자가 **없다고 오해**(데이터 일관성 43 §9) — 배지 없이 끄는 건 금지.
- 서버 승격 = 다른 도구들의 공통 답 · 우리는 이미 두 길(`filter.requery` 새 탭 · 조건 바 같은 탭)이 있어 **합치기만** 하면 된다. 로컬 폴백은 상한 + 배지 + 수동 버튼으로 오해를 막는다.

### 4-3. 바뀌는 자리

| 자리 | 변경 |
|---|---|
| `grid.rs` `clamp()` | `my == 0 && filters` 분기 → `fill_pages_left > 0` 조건 · 페이지 수신에서 −1 · 필터 변경에서 리셋 |

## 6. 시험

- 단위: `DistinctIndex` 난수 대조(HashSet<String> 모델 · 증분 = 한 번에 만든 것과 같음) · 종속 목록(통과 행만) · `fetch_under_filter` MC/DC(6조건) · `fill_pages_left` 카운터.
- 자체 시험(기동 명령): `grid.vpick` → `grid.vpick.dump`에 `total=d built=n/N` · 서버 길은 격리 SQLite로 `[서버에서 값 읽기]` 클릭 → 1열 결과 · 필터 추가 뒤 `result.dump`에 `src=` 감싼 SQL(서버 승격) · `grid.filter_server=local`에서 페이지 수 = 3에서 멈춤(`fetch.dump`).
- 실기(U-196): 실서버 Oracle 8만 행 ITEM_CD `P` 검색 = 값 전부 · 필터 걸고 스크롤 = 재조회 1회 뒤 보통 페이지.

## 7. 작업 순서

1. **T-285 B 먼저**(사용자 체감 결함 · 작음): 채움 카운터 + `filter_server` 설정 + 같은 탭 서버 승격(조건 바 길 재사용) + 배지·버튼 + MC/DC.
