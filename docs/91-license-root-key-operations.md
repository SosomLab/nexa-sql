# 91. 라이선스 루트 키 운영 지침 — 생성 · 사용 · 보관 · 이동 · 회전 · 유출 대응

> 사용자 09-27: *"발급기는 오픈소스를 써서 임의로 만들 수 있어선 안 된다 — 기준 정보 생성·사용·보관·이동 방법을 문서로."*
> 설계 = [23](23-license-activation.md) · [25 §9·§12](25-license-tiers-and-server.md) · 결정 D-27 · D-48. 이 문서는 **운영자(SosomLab) 전용 절차**다.

## 0. 한 장 요약 — 무엇이 비밀인가

| 공개돼도 되는 것 | **비밀** |
|---|---|
| 라이브러리 코드(`nexa-license`) · 형식(`nxl1`) · 검증 코드 · **루트 공개키**(`keys.rs`) · 발급기 코드(비공개 저장소지만 유출돼도 발급 불가) | **루트 비밀키**(32바이트) 하나 — 이것을 가진 자만 앱이 받아들이는 라이선스를 만들 수 있다 |

원리: 앱은 내장된 **공개키**로 서명을 검증한다. 오픈소스로 발급기를 똑같이 만들어도 **다른 비밀키**로 서명한 파일은 앱이 거부한다. 따라서 안전 = "비밀키가 발급 PC 밖으로 나가지 않는 것" 하나로 환원된다(docs/23 §2-3 "정직한 한계": 앱 바이너리 패치는 어느 로컬 인증도 못 막는다 — 목표는 정직한 고객이 쉽게, 우회는 귀찮게).

## 1. 기준 정보 생성(최초 1회 · 발급 PC)

1. 발급 PC 준비: 운영자 1인만 쓰는 계정 · 디스크 암호화(BitLocker/FileVault/LUKS) · 클라우드 동기화 폴더 **밖**의 작업 폴더(예 `~/nexa-issuer/`).
2. `nexa-license-tool keygen --out ~/nexa-issuer/root-v1.key --id root-v1` — 암호 두 번 입력(`--pass-env NEXA_LICENSE_KEY_PASS`도 허용 · 인자로는 못 준다 · 같은 경로가 있으면 덮어쓰지 않는다).
   - 산출 = **봉투 파일** `root-v1.key`(형식 `nxk1` · PBKDF2-HMAC-SHA256 60만 회 → 키 · HMAC 스트림 XOR + MAC · 유닉스 0600 · 외부 crate 0) + **공개키** `root-v1.key.pub`(형식 `nxp1` · base32).
3. 공개키를 라이브러리에 박는다: `nexa-license-tool keys-rs ~/nexa-issuer/root-v1.key.pub --out <nexa-license>/crates/nexa-license/src/keys.rs`(회전 때는 `.pub` 둘을 나란히) — **공개 저장소에 올라가도 된다**. 커밋 메시지에 공개키 base32 앞 8자를 적는다.
4. 앱을 다시 빌드·배포한다(공개키가 바이너리에 들어간다). 발급 뒤 `nsql license status`의 `state licensed`가 확인이다.
5. **곧바로 백업**(§3)을 만든 뒤에야 첫 발급을 한다.

⚠ 09-27 현재 `ROOT_KEYS`는 **비어 있다**(키를 아직 만들지 않았다 — 발급 PC에서 만드는 것이 원칙). 개발 시험은 시험 전용 키를 코드 안에서 만들어 쓴다(`with_roots` · 실 키와 무관).

## 2. 사용(발급 때마다)

- 발급은 **발급 PC에서만**. `issue`는 봉투를 메모리에서 풀고 서명 뒤 즉시 지운다(디스크에 평문 비밀키를 쓰지 않는다).
- 암호는 프롬프트 또는 `--pass-env NEXA_LICENSE_KEY_PASS`(셸 히스토리에 안 남게 `read -s`로 넣는다) — 스크립트 파일에 적지 않는다.
- 발급 = `nexa-license-tool issue --key root-v1.key --request <코드> --kind user --licensee "<이름>" --tier pro [--email …] [--note 주문번호]` → `./issued/<ID>/nexa-sql.license` + `mail.txt` · 기기 추가 = `reissue --id <ID> --add-request <코드>`(옛 판은 `.v<N>`으로 보존).
- 대장 `ledger.tsv`는 발급 PC 로컬(§3 백업에 포함) — 기기 ID는 접두 8자만 적는다(요청 코드 원문 보관 불필요).
- 발급한 파일은 `verify`로 자기 검증 뒤 전달한다(같은 검증 코드 = 앱과 동일 판정).

## 3. 보관·백업

| 사본 | 어디 | 무엇 |
|---|---|---|
| 원본 | 발급 PC(암호화 디스크 · 동기화 폴더 밖) | 봉투 + 대장 |
| 오프라인 1 | 금고의 USB(암호화) | 봉투 + 대장 + **암호는 함께 두지 않는다** |
| 오프라인 2 | 다른 장소의 USB 또는 종이(봉투 base32 출력 · 32B라 한 장) | 봉투만 |
| 암호 | 운영자 기억 + 봉인된 종이 1장(오프라인 1과 **다른 장소**) | — |

- 저장소(공개·비공개 모두)에 봉투를 **절대 커밋하지 않는다** — `nexa-license-server/.gitignore`에 `*.key` · `ledger.tsv` · `issued/`.
- 이메일·메신저·클라우드 드라이브로 봉투를 보내지 않는다.
- 백업은 분기 1회 `verify`로 살아 있는지 확인(USB 열화).

## 4. 이동(발급 PC 교체)

1. 새 PC를 §1-1처럼 준비.
2. 봉투를 **물리 매체**(암호화 USB)로 옮긴다 · 암호는 별도 채널(구두/종이).
3. 새 PC에서 `nexa-license-tool verify <아무 발급 파일>` + `keygen --show ~/nexa-issuer/root-v1.key`(공개키·지문 출력)로 지문이 `keys.rs`와 같은지 확인.
4. 옛 PC의 봉투·대장을 **안전 삭제**(암호화 디스크면 폴더 삭제로 충분 · 아니면 덮어쓰기) · 옛 PC가 남아 있으면 계정 잠금.
5. 대장 마지막 줄 번호를 새 PC에서 이어 간다(ID 채번 연속성).

## 5. 회전(계획된 교체 · 2~3년 또는 의심 시)

1. 새 키 `root-v2` 생성(§1) → `keys.rs`의 `ROOT_KEYS`에 **추가**(v1 유지) → 앱 배포.
2. 앱이 충분히 갱신된 뒤(예 6개월) 발급을 v2로 전환(`issue --key root-v2.key` · 파일에 `key=root-v2`).
3. 모든 앱이 v2를 아는 시점에 v1을 `ROOT_KEYS`에서 뺀다 → 옛 파일은 계속 유효(서명 검증은 발급 당시 키로 · 앱이 v1을 빼는 순간부터 v1 파일은 거부되므로 **뺄 때는 v1 발급분 재발급을 먼저**(D-48 재발급 프로세스)).
4. v1 봉투 파기(백업 포함).

## 6. 유출 대응(비밀키가 새어 나갔다고 의심될 때)

1. 즉시 v2 생성 · `keys.rs`에서 **v1 제거 + v2 추가** · 긴급 앱 판 배포.
2. 대장 기준으로 정당한 v1 보유자 전원에게 **무상 재발급**(v2 서명 · 같은 id) — D-48 프로세스.
3. 유출 경로 기록(journal) · 백업 매체 교체.
4. 앱 쪽: v1로 서명된 파일은 새 판에서 `Invalid(NoRootKey)`가 되므로 안내 문구에 "재발급 요청"을 명시.

## 7. 분실(비밀키를 잃었을 때)

- 기존 라이선스는 **계속 유효**(검증만 하면 되니까). 새 발급만 불가 → §5로 v2 생성·배포 후 v2로 발급. v1 보유자 재발급은 불필요(v1 공개키를 계속 내장).
