# 59 · 대용량 파일 처리 — 다른 편집기 비교 · 이번에 고친 것 · 개선 제안 (사용자 요청 09-19)

> **요구**: ① 성능 향상을 위해 고칠 곳을 정리하고 설계 변경·최적화 진행 ② 메모리 회수(큰 파일 닫기 · 접속 해제 · 결과 폐기)를 전수 점검하고 "즉시 1회 + 주기" 회수 ③ 대용량 파일의 편집·관리 방식을 다른 편집기와 비교해 개선안 제안.
> **상태**: ①② ✅(journal 82차) · ③ **✅ 1·3단계**(83차 · §5) · **✅ 2단계 = 편집 버퍼 교체 T-142**(09-20 · journal 84차 · **§6**) — D-125~128 전부 권장안대로. 남은 것 = §6-4. 관련: [55 입력 지연](55-editor-input-latency.md) · [26 §7-3·7-4 메모리](26-performance-architecture.md) · [60 되돌리기 재설계](60-undo-redo-redesign.md) · [58 외부 변경](58-external-change-policy.md).

## 0. 결론

1. **측정으로 찾은 병목 다섯**을 고쳤다 — 전부 "매 프레임/매 키마다 본문 전체를 다시 훑는" 종류였다. 4만 줄·3.6 MB 스크립트(전 기능 켬) 기준: 유휴 그리기 **78 → 3.3 ms** · 글자 입력 **209 → 16 ms** · 앱 유휴 CPU **812 → 188 ms/6초**.
2. **가장 큰 메모리 위험은 되돌리기였다** — 묶음마다 본문 전체(`Vec<char>` = 4 B/글자)를 복사했고 상한이 1,000개라, 100 KB 스크립트도 오래 편집하면 수백 MB까지 갈 수 있었다. → **전체 복사 1개 + 차이만** 저장.
3. **회수는 이미 대부분 잘 되고 있었다**(큰 탭 닫기 41.5 → 10.5 MB · 10만 행 결과 교체 41.1 → 10.6 MB — 기준선까지). 여기에 힙 → OS 정리(즉시 1회 + 유휴 주기)와 보이지 않는 탭의 캐시 해제를 더했다.
4. 남은 구조적 비용은 **버퍼 표현**이다: `Vec<char>`(4 B/글자) + 저장 기준 `String` + 줄 변경 기준선 = 파일의 ≈ 6.6배. 주류 편집기는 1.0~1.1배다. → §4 2단계(UTF-8 갭 버퍼 + 줄 시작 표) 제안.
5. SQL 클라이언트다운 해법은 "큰 스크립트를 **열지 않고 실행**"이다(DataGrip · DBeaver 네이티브 실행 · sqlcmd · SQLcl 모두 이 길) → §4 3단계.

### 2-2. 회수 정책(`memtrim.rs` · `main.rs mem_*`)

- **즉시 1회**(`mem.trim_on_release` 기본 켬): 탭 수가 줄었을 때 · 마지막 탭을 비웠을 때 · 실행이 끝났을 때(앞선 결과를 놓음) · 접속이 끊겼을 때 → **1초 뒤**(해제가 끝나고 · 연달아 일어나도 한 번) 회수.
- **주기**(`mem.trim_secs` 기본 300 · 0 = 끔): 입력 없음 5초 + 실행 중 세션 없음일 때만. 바쁘면 10초 뒤 다시 본다.
- **회수 한 번** = ① 보이지 않는 탭의 그리기 캐시 해제 ② 힙 정리 — Windows `HeapSetInformation(HeapOptimizeResources)` + 모든 힙 `HeapCompact` · Linux `malloc_trim(0)` · macOS `malloc_zone_pressure_relief`. **워킹셋 트림은 하지 않는다**(26 §7-2 ③ — 숫자만 줄고 복귀 때 느려진다).
- 수동: 팔레트 **"View: Release Unused Memory Now"**(전후 Private를 상태줄에). 개발자 모드(`load` 층)에는 회수마다 전후·걸린 시간이 남는다 · `NSQL_TRACE_MEM`.

### 2-3. 실측(Release · Private Bytes · 격리 설정 폴더 · `@after:` 기동 명령)

## 4. 제안(3단계 · 결정 D-125~D-128)

### 1단계 — 버퍼 구조를 두고 하는 것(✅ 대부분 이번에 함)

- ✅ 세대(`rev`)로 묶은 캐시 · 보이는 곳만 계산 · 구문 상태 지연 계산(Scintilla `end styled`와 같은 생각) · 본문 전체 `String` 재조립 제거 · 되돌리기 차이 저장 · 임시 할당 회수.
- ☐ **큰 파일 모드**(VS Code·Notepad++식 · 설정 레지스트리 · 바이트와 줄 수 둘 다):

  | 단계 | 기준(안) | 끄거나 줄이는 것 |
  |---|---|---|
  | L1 | 5 MB 또는 10만 줄 | 미니맵 = 간격 표본 · 선택어 강조 끔 · 괄호 짝 표 = 화면 ±N줄 · 줄 변경 기준선 = 줄 해시만(5 MB → 320 KB) |
  | L2 | 20 MB 또는 30만 줄 | 구문 강조 · 줄 접기 · 줄 변경 표시 · 자동 병합(58) 끔 · 2만 자 넘는 줄은 토큰화 안 함 |

  상태줄에 **"큰 파일(L2)"** 표식 — 누르면 기능별 토글 + "강제로 켜기"(VS Code). → **D-125**
- ☐ 저장 기준 `String`을 없애고 되돌리기 스택의 "저장 지점" 표식으로 대체(−파일 크기) — 더러움 판정·외부 변경 병합(58)의 base는 줄 해시 + 필요할 때 디스크에서 다시 읽기.

### 2단계 — 버퍼 표현 교체(설계 변경 · **D-126**)

| | 갭 버퍼(UTF-8) | piece table/tree | 로프 |
|---|---|---|---|
| 메모리 | 1.0배 + 갭 | ≈ 1.0배 + 추가 버퍼(원본을 저장 기준·기준선으로 겸용 · mmap 가능) | ≈ 1.1배 |
| 가까운 편집 | O(1) | O(log p) | O(log n) |
| 먼 곳으로 점프 | memmove(100 MB ≈ 2 ms) | O(log p) | O(log n) |
| 다중 커서 | 오프셋 순서로 한 번 쓸기(100 MB ≤ 2 ms) | 좋음 | 가장 좋음 |
| 줄 찾기 | 별도 줄 시작 표 | 조각별 줄 시작 + 트리 합계 | 요약 |
| 검색 | 연속 메모리 — 가장 빠름 | 조각 단위 | 조각 단위(≈ 7배 느림) |
| 자체 구현 규모(어림) | 400~700줄 | 1,200~2,000줄 | 1,500~2,500줄 |

**권장 = UTF-8 `Vec<u8>` 갭 버퍼 + Scintilla식 줄 시작 표**(줄 시작도 갭 버퍼 · "계단" 지연 오프셋이라 편집 O(1) · 줄→오프셋 O(1)). 이유: 셋 중 가장 작고 · Scintilla·Emacs가 증명했고 · 검색이 가장 빠르고 · 3.6 MB 파일이 24 MB → ≈ 4 MB가 되며 · 우리 상한(100 MB)에서 최악의 갭 이동이 수 ms다. 버퍼 접근을 포트(`slice(range)` · `line_start(n)` · `line_of(off)` · `replace(range, &str)`) 뒤에 두면 나중에 100 MB 넘는 mmap 파일·백그라운드 스냅샷이 필요할 때 piece tree로 바꿀 수 있다. 로프는 파서 스레드·협업을 넣을 때만 값을 한다. 커서·열은 바이트 오프셋으로 두고 글자·칸 변환은 보이는 줄에서만.

되돌리기 = 연산 기록(Scintilla) `{오프셋 · 지운 글 · 넣은 글 · 앞뒤 커서}` · 묶음 단위 · 인접 타이핑 병합. **메모리 상한**(→ **D-127**): 개수(`editor.undo_max`)가 아니라 **바이트 예산** `max(16 MB, min(파일 × 2, 256 MB))` · 오래된 묶음부터 버림 · 저장 지점이 버려지면 "영구 더러움" · 예산을 넘는 단일 연산(L2의 전체 바꾸기)은 "되돌릴 수 없습니다 — 계속?".

영향 범위: nexa-ctl `EditState`(캐럿·선택·다중 커서가 char 인덱스) · `TextBox` 전반 · nexa-sql의 char 인덱스 호출부(찾기·실행 범위·오류 줄). 큰 작업이라 **T-142로 분리**하고 포트 도입 → 구현 교체 → 호출부 이관의 3보로 나눈다.

### 5-2. 적재 — 탭 안에 격리된 진행 막(사용자 09-20)

요구가 하루 안에 두 번 왔다: ① "기준 이상 파일은 편집창 가운데에 진행 막대 · 100% 뒤에 편집 화면 · **그동안 다른 작업·키 입력 금지**" → ② "**로딩 중에도 다른 탭 추가·편집·실행이 되게 분리**". 뒤의 지시를 따랐다(충돌·조정 = journal 83차).

- **자리 탭**: 기준(`file.async_load_mb` 8 MB) 이상이면 그 파일의 탭을 **먼저** 만든다 — 비어 있고 · 읽기 전용이며 · **경로가 없다**(저장해도 원본을 덮지 않는다) · 제목 `이름 …`. 진행 막은 **그 탭이 활성일 때만** 편집 영역 가운데에 뜬다. 다른 탭·새 탭·열기·실행·접속은 그대로다.
- **막는 것은 그 탭의 본문을 쓰는 명령뿐**(`fileload::blocked_while_loading` — `edit.*`·`find.*`·`run.*`·저장류 · 단위 테스트) → 상태줄 "이 탭은 아직 읽는 중". **Esc = 그 적재 취소**(자리 탭을 닫는다) · 자리 탭을 닫아도 취소 · 스레드는 다음 1 MB 덩어리에서 멈춘다.
- **무거운 일은 전부 스레드에서**: 읽기(1 MB 덩어리 · 진행값 = 원자값) → 글자 풀이 → **편집기 본문 준비**(nexa-ctl `PreparedText` — 글자 버퍼 + 본문 문자열 + 줄 표 · `Send`). UI 스레드는 `TextBox::set_prepared`로 **옮겨 받기만** 한다(65 MB에서 0.0 ms). 끝나도 **활성 탭을 빼앗지 않는다**.
- **진척도는 실제 값**: 읽은 바이트 0~80% · 글자 풀이 85% · 본문 준비 92% · 받은 뒤 100%. 막이 보이는 중이면 **100% 프레임을 한 번 그린 뒤에** 편집 화면으로 바꾼다.
- **기준 = 둘**(적당한 기준을 찾아 달라는 요구): 크기 8 MB(그 아래는 이 PC에서 0.15초 안쪽 — 동기로 읽는 편이 단순하고 빠르다) **그리고** 경과 `file.load_progress_ms` 300 ms(그 안에 끝나면 막을 아예 안 보인다 — 0.1초짜리 번쩍임 방지 · "1초 넘으면 진행 표시"의 앞단). 빠른 SSD에서는 대략 30 MB부터, 느린 디스크·공유 폴더에서는 8 MB부터 보이게 된다.
- **열지 않고 실행**은 읽는 사이 활성 탭이 바뀌면 **실행하지 않는다** — 실행은 활성 탭의 세션으로 가므로, 고른 것과 다른 접속(운영일 수도 있다)에서 큰 스크립트가 돌 뻔한 경우다.
- 같은 파일을 또 열면(열려 있거나 읽는 중이거나) 읽지 않고 그 탭으로 간다.

### 6-1. 무엇으로 바꿨나

nexa-ctl `edit/textbuf.rs` **`TextBuf` = UTF-8 갭 버퍼 + 줄 시작 표**(권장안 ① 그대로 · 외부 crate 0 · `unsafe` 0).

- **저장**: `Vec<u8>` 하나에 갭(빈 구간) 하나 — 글자당 1 B(ASCII)~3 B(한글). 종전 `Vec<char>` = 글자당 4 B.
- **좌표는 글자 인덱스 그대로**(설계 제안과 다른 점 — 아래 6-3): 캐럿·선택·되돌리기 기록·호스트의 찾기/실행 범위/오류 줄이 모두 글자 단위라, 바이트 오프셋은 버퍼 안에서만 쓴다. 글자 → 바이트는 줄 표 이분 탐색 + **ASCII만 있는 줄은 O(1)**(글자 수 == 바이트 수) + 직전 자리에서 걸어가는 위치 캐시.
- **줄 표를 편집과 함께 고친다**(줄마다 `바이트 시작 · 글자 시작`): 바뀐 줄만 갈고 뒤는 밀기만 한다(70만 줄에서 0.3 ms). 줄 ↔ 글자, 캐럿의 줄·열, 선택이 걸친 줄 수가 전부 O(log 줄 수).
- **변경 기록**(`LineChange{first, removed, inserted}` · 통째 교체 세대 `epoch`): 줄별 캐시(폭 · 구문 상태)를 가진 그리기 쪽이 **바뀐 줄만** 고친다.
- **그리기는 보이는 줄만 꺼낸다**(`Rows` — 접지 않으면 버퍼의 줄이 곧 행 · 갭에 걸친 줄 하나만 새 문자열). 종전에는 프레임마다 모든 줄의 (시작, 글) 목록을 만들었고, 편집할 때마다 본문 전체를 문자열로 다시 모으고 전 행을 해시했다.
- **조합 중(한글 IME)**: 캐럿 줄 **하나에만** 조합 글자를 끼운다(종전 = 조합하는 동안 프레임마다 본문 전체를 새 문자열로).
- **여러 곳 편집**: 64곳 이하는 한 곳 바꾸기를 뒤에서부터 되풀이(O(편집) · 캐시 유지) · 그보다 많으면 본문을 한 번 훑어 새로 짓는다.
- 접기(wrap) 모드는 종전 경로(본문 문자열 + 행 해시)를 그대로 쓴다 — 행이 줄과 다르고 가로 스크롤이 없어 폭도 필요 없다.
- `PreparedText` = `TextBuf`를 작업 스레드에서 만든 것(문자열의 바이트가 **복사 없이** 본문이 된다 · 줄 표 한 번 훑기만).
- 호스트: `TextBox::chars() -> &[char]` 폐지 → `buf() -> &TextBuf`(`get` · `slice` · `iter_from`/`iter_rev_from` · `line_of`/`line_start`/`line_text` · `find` · `eq_str` · `content_hash`). 캐럿 줄·열 · 선택 요약 · 저장본 비교 · 큰 파일 단계 판정이 본문을 훑지 않는다. **찾기**는 줄 단위로(종전 = 찾기 입력마다 본문 전체를 문자열 + 글자 배열로 — 65 MB 파일 = 임시 325 MB).

### 6-3. 설계 제안과 달라진 것(충돌·조정)

- **좌표 단위**: §4는 "캐럿·선택을 바이트 오프셋으로 · 3보(포트 → 구현 → 호출부 이관)"였다. 구현은 **글자 인덱스 유지**다 — 호출부(편집 명령 36곳 · 텍스트 상자 26곳 · 호스트 · 되돌리기 기록 · 기록 파일 형식)를 바이트로 옮기면 한글 경계 버그의 표면이 그만큼 넓어지는데, 얻는 것은 글자 → 바이트 변환 비용뿐이고 그 비용은 줄 표 + ASCII 지름길 + 위치 캐시로 측정상 보이지 않는다(입력 3 ms). 포트(trait)도 두지 않았다 — 구현이 하나다(30 §1-2 "두 번째를 만나면 부품으로").
- **줄 표의 "계단" 지연 오프셋**(Scintilla)도 쓰지 않았다 — 뒤따르는 줄을 미는 단순한 방식이 70만 줄에서 0.3 ms다. 100만 줄을 넘는 파일이 현실이 되면 그때 넣는다.

### 6-4. 남은 것

- **편집마다 본문 전체를 보는 기능 둘**: 줄 변경 표시(기준선 비교)와 괄호 짝 표 — 둘 다 본문을 문자열로 다시 만든다(4만 줄에서 입력 7.5 ms의 대부분). 큰 파일 모드는 끄고 · 괄호 표는 `max_chars` 상한이 있어 위험은 없지만, 변경 기록으로 줄 단위 갱신하면 보통 파일의 입력이 2~3 ms가 된다 → **T-145**.
- **정규식 찾기 · 여러 줄 질의 · 실행(문장 분할)**은 본문을 문자열로 만든다(엔진이 문자열 하나를 요구) — 동작마다 한 번이라 상주 비용은 없다.
- 스트리밍 문장 분할기 · N문장 넘으면 페치 끔 · 인코딩 표본 판정 · tail 따라가기(§5-1 그대로).
