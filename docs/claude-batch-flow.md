## 1. 왜 — 세 조건

단계마다 명령 하나를 돌리고 출력을 읽고 다음 명령을 정하면, 왕복마다 문맥(토큰)이 쌓이고 사람도 기다린다. 대신 **사전에 점검한 절차를 한 번에 순차로 돌리고(Blackbox) 입력 → 출력(요약)만 보고 분석한 뒤 다시 진행**한다. 이것이 효과를 내려면 세 조건이 필요하다(사용자 문장 그대로):

1. **출력이 짧고 구조적이어야 한다** — 긴 로그를 통째로 읽으면 절약 효과가 사라진다 · 단계별 통과/실패 · 소요 시간 · 첫 오류 몇 줄만 담은 요약을 만들고 원 로그는 실패한 단계 것만 연다.
2. **실패해도 끝까지 간다** — 첫 실패에서 멈추면 고치고 다시 돌리는 왕복이 그대로 남는다 · 싼 단계(형식 검사)를 앞에 두고 전부 돌린 뒤 실패를 한꺼번에 본다.
3. **형식화할 수 없는 일은 대화식이 맞다** — 처음 보는 실패의 원인 추적 · 아직 절차가 없는 새 종류의 작업 · 되돌릴 수 없는 일의 확인 · 사용자 결정 질문 · 이런 일도 같은 종류를 두 번째 만나면 절차로 올린다.

Blackbox의 약점은 **도는 동안 안이 안 보인다**는 것이다. 이것은 세션이 대화로 캐물어(폴링) 메우지 않고, **흐름이 스스로 흔적을 남기게** 해서 메운다(§6).

## 2. 무엇을 흐름으로 묶고 무엇을 대화식으로 남기나

| 흐름으로 묶는다 | 대화식으로 남긴다 |
|---|---|
| 형식 검사 · 정적 분석 · 단위/통합 시험 · 빌드 · 기동 확인 | 처음 보는 실패의 원인 추적 |
| 화면·동작 확인(덤프 + 기대 문자열 · §8) | 아직 절차가 없는 새 종류의 작업(두 번째부터는 절차로) |
| 패치 적용 → 형식 → 정적 분석 → 시험(한 명령) | 되돌릴 수 없는 일의 확인(삭제 · 강제 push · 배포) |
| 측정(같은 조건 N회 · 평균) | 사용자 결정 질문 |

판단 기준: "다음에 같은 일을 또 하면 같은 순서로 할 것인가?" — 그렇다면 흐름이다.

## 3. 흐름의 모양 — 수준과 단계 순서

- **진입점은 하나**(`verify` 같은 이름 · 수준 인자 `--level`). 수준이 올라갈수록 앞 수준을 포함한다.

| 수준 | 언제 | 단계(싼 것 먼저) |
|---|---|---|
| `quick` | 편집 직후 · 커밋 전 | 형식 · 정적 분석 · 기록 형식 검사 |
| `v2` | 기능 단위 완료 · 병합 전 | quick + 단위 시험 · 통합 시험 · 빌드 · 화면 시나리오(선택) |
| `prepush` | push 직전 1회 | quick + 단위 시험 + 더 엄격한 정적 분석(새 툴체인 등) |
| `full` | 릴리스 직전 · 사용자 요청 | v2 + 교차 플랫폼 · 무거운 선택 구성 포함 |

- **순서 원칙**: 몇 초짜리(형식) → 분 단위(정적 분석 · 단위) → 외부 의존(통합 · 실서버) → 빌드 → 화면. 싼 단계 실패도 **끝까지 간다**(`--fail-fast`는 선택).
- **같은 일을 두 번 하지 않는다**: 정적 분석은 한 번만 · 빌드 산출 폴더는 되도록 하나(분리가 필요하면 이유를 적고 하나만 더) · 단계마다 **같은 패키지·기능 집합**을 넘겨 다시 컴파일되지 않게 한다.
- 단계는 **한 함수 = 한 판정**. 함수 안에서 출력이 길면 시험 프레임워크의 "통과한 줄"을 걸러 로그를 작게 둔다.

## 4. 단계 규약 — 결과 넷 · 로그 · 외부 조건

| 결과 | 조건 | 실패 수에 |
|---|---|---|
| `PASS` | 종료 0 | — |
| `FAIL` | 종료 0 · 99 · 124 외 | +1 |
| `SKIP` | 종료 99 = **판정 불가**(외부 조건 없음: 서버 미도달 · env 없음 · 실행 중인 창 때문에 빌드 불가) — 마지막 줄 = 이유 | — |
| `TIMEOUT` | 단계 상한 초과 → 그 단계가 띄운 **프로세스 트리만** 종료 | +1 |

- 로그 = `<출력 폴더>/<단계>.log` 하나(표준 출력 + 오류 합침). 요약에는 경로만 쓴다.
- "SKIP 판정 불가"는 통과가 아니다 — 요약에 그대로 남겨 다음 사람이 "안 돌았다"를 알게 한다.
- 외부 조건 검사(도달 · 자격 증명 · 실행 중 프로세스)는 단계 **맨 앞**에서 싸게 한다(몇 초 · 짧은 상한).

## 5. 요약 규격

한 실행 = 폴더 하나(`<출력 루트>/verify/<YYYYmmdd-HHMMSS>/`). 그 안의 `summary`가 **유일하게 읽는 파일**이다.

```
# verify 20261121-213000 · level=v2 · v1=conn-role · a1b2c3d4

| 단계 | 결과 | 초 | 메모 |
|---|---|---|---|
| fmt | PASS | 3 | |
| lint | FAIL | 412 | rc=101 · …/lint.log |
    error[E0425]: cannot find value `x` in this scope
    --> src/app/x.rs:12:5
| test | PASS | 180 | test result: ok. 1203 passed |
| it | SKIP | 2 | SKIP 판정 불가(사내 DBMS TCP 도달 실패 1곳) |
| build | TIMEOUT | 1800 | 상한 1800s 초과 · 프로세스 트리 종료 · …/build.log |

실패 단계 2 · 로그 = …/verify/20261121-213000
```

- 머리 줄 = 시각 · 수준 · 선택 인자 · 커밋 해시(어느 코드를 판정했는지).
- 행 = 단계 · 결과(§4) · 소요 초 · 메모(PASS = 한 줄 집계 · SKIP = 이유 · FAIL/TIMEOUT = 로그 경로). FAIL/TIMEOUT 바로 아래에 **첫 오류 5줄**(들여쓰기 4칸 · 200자 자름).
- **단계가 끝날 때마다 행을 덧붙인다**(끝에 한 번 쓰지 않는다 — 도는 중에도 지금까지의 결과가 보인다).
- 끝 줄 = 실패 단계 수 · 로그 폴더. **종료 코드 = 실패 단계 수**(0 = 전부 통과).
- **이력** = `<출력 루트>/verify/history.tsv`(수준 · 단계 · 소요 초 · 날짜) — 예상 종료·상한 계산(§6)에 쓴다.
- 읽는 순서: summary → 실패 단계의 첫 오류 5줄 → 모자랄 때만 그 단계 로그(통째가 아니라 `grep`·앞뒤 몇 줄).

## 6. 진행 상황을 보이는 법

원칙: **보는 쪽이 묻지 않아도 파일만 열면 알 수 있게**. 세션이 대화로 상태를 캐묻는 폴링은 쓰지 않는다(예외 = ⑩ 원격 작업자).

| # | 항목 | 하는 법 |
|---|---|---|
| ① | **작업판** | 5분 넘게 걸릴 일은 시작할 때 `무엇 · 누가 · 시작 · 예상 소요`, 끝나면 `결과 · 실제 소요`. 모든 세션·하위 에이전트 공용 파일 하나(덧붙이기만 = 잠금 없이 안전) → 사람이 읽는 현황 문서가 사건마다 다시 만들어진다 |
| ② | **진행률** | 단계가 바뀔 때마다 `n/N · 지금 단계`. 요약은 단계가 끝날 때마다 덧붙임(§5) |
| ③ | **예상 종료** | 남은 단계들의 이력 중앙값(최근 3회) 합. 이력이 없으면 **"예상 없음"**(지어내지 않는다) |
| ④ | **살아 있다는 신호** | 긴 단계는 30~60초마다 경과 + 로그 마지막 줄. 신호가 3분 넘게 끊기거나 예상의 3배를 넘으면 **"⚠ 멈춤 의심"** |
| ⑤ | **시간 상한** | 단계마다 상한 = 이력 중앙값 × 3(최소 2분 · 최대 60분 · 이력 없으면 단계별 기본값) → 넘으면 `TIMEOUT` 적고 **자기 프로세스 트리만** 끄고 다음 단계로 |
| ⑥ | **첫 실패 즉시 표시** | 끝까지 가되, 첫 실패가 난 순간 현황 문서 **맨 위**에 `✗ <일>: 첫 실패 = <단계> · <첫 오류 한 줄>` |
| ⑦ | **무엇이 도는지** | 신호에 단계 PID를 넣고, 한 화면 보기에 프로세스(PID · 이름 · 시작 · CPU · 작업 폴더)를 함께 |
| ⑧ | **한 화면 보기** | 명령 하나(`status` · `--watch`)로 진행 중 · 최근 끝난 일 · 프로세스 · 저장소 상태 · 마지막 CI. 현황 문서는 편집기에 열어 두면 저절로 갱신 |
| ⑨ | **대리 기록** | 작업판에 직접 쓸 수 없는 작업자(다른 PC · 클라우드 세션 · 하위 에이전트)의 일은 **맡긴 마스터 세션이** 적는다 — 작업자 칸 = `개발 \| 협업 \| 하위:<이름> \| 원격:<이름>` · 적은 이 = `자기` 또는 `대리:<마스터>` · 마스터가 확인할 때마다 "확인 21:40(12분 전)"이 남아 **오래된 정보임이 보인다** |
| ⑩ | **원격 위임 감시** | 아래 소절 |

### 6-1. 원격 작업자(⑩)

원격 작업자(다른 PC의 원격 제어 세션 · 클라우드 세션)는 **이 PC에 흔적을 남길 수 없다** — 그래서 "대화로 캐묻지 않는다"의 예외로, 마스터가 정해진 주기로 확인한다.

1. **위임 즉시 응답 확인** — 맡긴 직후 수신·착수 응답을 확인하고 `ack`를 적는다. 없으면 현황 문서에 **"⚠ 응답 미확인"**이 남는다.
2. **10분에 한 번 확인** — 마지막 확인 뒤 10분이 지나면 현황 문서에 **"⏰ 확인할 때"**(마스터가 놓치지 않게). 확인하면 진행·확인 시각을 적는다.
3. **살아 있음 ≠ 진행** — 확인할 때마다 **진행 증거** 한 줄(지금 단계 · 새 커밋 해시 · 산출 파일 수 · 로그 줄 수)을 적는다. 지난 확인과 증거가 같으면 "정체 1회".
4. **두 번 연속 정체** = 멈춤으로 본다 — 현황 문서 맨 위에 **"✗ 원격 <이름> 진행 없음(N분)"** · 사용자에게 알리고 조치(재지시 · 회수 · 다른 작업자).
5. 되돌려 답할 수 없는 작업자(클라우드 세션 등)는 마스터가 **그쪽 기록을 읽을 때** 갱신하고 그 시각을 확인 시각으로 남긴다.
6. 하위 에이전트(마스터가 띄운 읽기 전용 조사 등)도 같은 길 — 띄운 세션이 시작·끝을 대신 적는다(조사 에이전트는 쓰기 금지).

## 7. 위임하는 법

위임(다른 세션 · 하위 에이전트 · 원격 작업자)도 **한 번에** 준다 — 중간 질문·알림 왕복을 없앤다.

```
[P1] V2 — <무엇을 바꿨나 한 줄>
절차: verify --level v2 --v1 <시나리오,…>   (추가 시나리오: <있으면>)
원하는 출력: summary 표 한 장 + 실패 단계의 첫 오류 5줄 · 그 밖은 쓰지 말 것
진행: 단계가 바뀔 때 `[진행] n/N · 지금 단계 · 예상 종료` 한 줄을 보낼 것(원격 · 되돌려 답할 수 있는 작업자만)
중간 알림: 실행 중인 창을 닫기 직전 · 실패가 났을 때만
```

- 받는 쪽 회신 = **요약 표 한 장**(결론 먼저 · 확인하지 않은 것을 됐다고 쓰지 않는다).
- 마스터는 `[진행]` 줄을 받을 때마다 작업판 `step`으로 옮긴다(⑨) · 원격이면 ⑩ 주기를 따른다.
- 조사 질문은 모아서 한 번에. 패치는 고칠 자리를 실제 파일로 먼저 한꺼번에 확인한 뒤 `적용 → 형식 → 정적 분석 → 시험`을 한 명령으로.

## 8. 화면·동작 판정 — 덤프 + 기대 문자열

- 화면을 눈으로 보지 않는다. 앱이 **상태를 글로 내보내는 명령**(덤프: 트리 · 표 · 상태줄 · 알림 · 대화상자 값)을 갖게 하고, 시나리오가 그 출력에 **기대 문자열이 있는지/없는지**를 대조한다.
- 시나리오 = 저장소 안 **재실행 가능한 파일 하나**(`<시나리오 폴더>/<이름>.sh`) · 결과 = PASS/FAIL 줄 + 덤프 파일.
- 격리: 설정 폴더는 매번 새 임시 폴더 · 창은 숨김/헤드리스 · **사용자 화면·입력·클립보드를 건드리지 않는다** · 끝나면 그 폴더 삭제(자격 증명 사본이 있으면 판정 직후).
- 앱 조작은 입력 주입 대신 **기동 명령**(환경 변수로 넘기는 명령 열)으로 몬다.
- 픽셀이 꼭 필요한 판정(겹침 · 잘림)은 창 단위 캡처 + 좌표 표본 대조로 하고, 그것도 시나리오 파일로 둔다.

## 9. 새 저장소에 들이는 순서(체크리스트)

1. 지금 손으로 하는 검증 명령을 순서대로 적는다(싼 것 → 비싼 것).
2. §10 뼈대를 `scripts/verify.sh`로 복사하고 단계 함수 다섯을 채운다.
3. 외부 의존 단계(DB · 네트워크 · 실행 중 창)는 맨 앞에서 검사해 99(SKIP)로 빠지게.
4. `--level quick`을 돌려 summary가 짧은지 본다(한 화면 안).
5. 일부러 실패를 하나 넣어 FAIL 행 + 첫 오류 5줄이 나오고 **다음 단계도 도는지** 본다.
6. 이력이 쌓이면 §6 ③⑤(예상 · 상한)를 켠다. 5분 넘는 흐름이면 작업판(①)과 한 화면 보기(⑧)를 붙인다.
7. 화면 판정이 필요하면 덤프 명령부터 앱에 넣고 §8 시나리오를 하나 만든다.
8. 저장소 규칙 문서(CLAUDE.md 등)에 "검증 = 이 명령 · 요약만 읽는다"를 한 줄 넣는다.
9. 같은 종류의 대화식 점검을 두 번째 하게 되면 시나리오·단계로 올린다.

## 10. 복사용 뼈대 스크립트

bash 하나 · 외부 도구 0. 단계 함수 다섯만 바꾸면 된다(2026-11-21 가짜 단계 PASS · FAIL · SKIP · `--fail-fast`로 실행 확인).

```bash
#!/usr/bin/env bash
# verify.sh — 검증 흐름 뼈대(언어 중립). 단계 = step <이름> <함수> · 실패해도 끝까지 · 요약 = out/verify/<시각>/summary.md
# 종료 코드 = 실패한 단계 수(0 = 전부 통과).
set -u
LEVEL=quick; FAILFAST=0
while [ $# -gt 0 ]; do case "$1" in --level) LEVEL=$2; shift 2;; --fail-fast) FAILFAST=1; shift;; *) shift;; esac; done
OUT="out/verify/$(date +%Y%m%d-%H%M%S)"; mkdir -p "$OUT"; SUM="$OUT/summary.md"; HIST="out/verify/history.tsv"; touch "$HIST"
printf '| 단계 | 결과 | 초 | 메모 |\n|---|---|---|---|\n' > "$SUM"
FAILN=0; STOP=0
step() {
  local name=$1; shift
  if [ "$STOP" = 1 ]; then printf '| %s | SKIP | 0 | fail-fast |\n' "$name" >> "$SUM"; return; fi
  local t0=$SECONDS; "$@" > "$OUT/$name.log" 2>&1; local rc=$? dt=$((SECONDS - t0))
  printf '%s\t%s\t%s\n' "$LEVEL" "$name" "$dt" >> "$HIST"
  case $rc in
    0)  printf '| %s | PASS | %s | |\n' "$name" "$dt" >> "$SUM" ;;
    99) printf '| %s | SKIP | %s | %s |\n' "$name" "$dt" "$(tail -1 "$OUT/$name.log")" >> "$SUM" ;;
    *)  FAILN=$((FAILN + 1)); printf '| %s | FAIL | %s | rc=%s · %s |\n' "$name" "$dt" "$rc" "$OUT/$name.log" >> "$SUM"
        grep -m5 -iE 'error|fail|panic' "$OUT/$name.log" | sed 's/^/    /' >> "$SUM"
        [ "$FAILFAST" = 1 ] && STOP=1 ;;
  esac
}
# ── 프로젝트에 맞게 바꾸는 곳: 단계 함수(종료 0 = PASS · 99 = SKIP(외부 조건 없음 = 판정 불가) · 그 밖 = FAIL) ──
s_format() { true; }   # 예: cargo fmt --check · npx prettier --check . · ruff format --check · gofmt -l .
s_lint()   { true; }   # 예: cargo clippy -- -D warnings · npx eslint . · ruff check · go vet ./...
s_unit()   { true; }   # 예: cargo test · npm test · pytest -q · go test ./...
s_it()     { true; }   # 예: 통합 시험(외부 DB가 없으면 echo "SKIP 판정 불가"; return 99)
s_e2e()    { true; }   # 예: 앱을 띄워 상태 덤프를 기대 문자열과 대조
# ── 순서(싼 것 먼저) ──
step format s_format
step lint   s_lint
step unit   s_unit
if [ "$LEVEL" != quick ]; then
  step integration s_it
  step e2e         s_e2e
fi
printf '\n실패 %s · 로그 %s\n' "$FAILN" "$OUT" >> "$SUM"
cat "$SUM"; exit "$FAILN"
```

- 명령을 환경 변수 문자열로 받지 말고 **함수로** 둔다(따옴표가 든 명령이 단어 분리로 깨진다 · 11-21 뼈대 시험에서 확인).
- 뼈대에 없는 것(§6 신호·상한·작업판)은 흐름이 5분을 넘기 시작할 때 부록 A의 `verify.sh` · `board.sh`에서 가져온다.

## 부록 B. 함정

- **Windows Git Bash**: `$!`는 MSYS PID — 프로세스 트리를 끄려면 `/proc/<pid>/winpid`로 바꿔 `taskkill //F //T //PID`. 백그라운드 bash 스크립트는 상위 작업을 멈춰도 살아남을 수 있다 — 끈 뒤 남은 빌드 프로세스 0을 확인.
- **Git Bash heredoc**: 도구를 거쳐 넘긴 heredoc에서 `\\`가 `\`로 줄 수 있다 — 역슬래시가 든 치환 스크립트는 파일 편집 도구로 쓰고 raw 문자열을 쓴다.
- **pyenv-win 셰임**: `python -`(표준 입력 스크립트)는 대화형으로 매달린다 · 인자의 `|`·괄호가 깨진다 → `.py` 파일 + `</dev/null`.
- **TCP 도달**: Git Bash `/dev/tcp` + `timeout`은 거짓 음성이 난다 — PowerShell `TcpClient.ConnectAsync().Wait(ms)`.
- **같은 빌드 폴더 동시 사용**: 두 흐름(두 세션)이 같은 빌드 폴더를 쓰면 잠금으로 서로 수십 분 멈춘다 — 빌드는 한 번에 하나(작업판으로 보인다).
- **측정은 진짜 편집으로**: 파일 시각만 바꾸는(`touch`) 재빌드는 실제 한 줄 수정과 소요가 다르다.
