## 3. 두 번 헛디딘 것 — 기록해 둔다

1. **기능 점검 1차에서 덤프 3건 실패**. 원인은 앱 결함이 아니라 **내 스크립트가 Debug exe를 기본으로 쓴 것**이었다.
   Windows판은 Release가 기본인데 Linux판만 Debug로 두어, Debug 기동(1.5 s)에 밀려 기동 명령이 실행되기 전에 프로세스를 끝냈다.
   - 실측: filterbar 첫 페인트 **Release 119 ms vs Debug 1,539 ms**. `nexa-sql` 자체 크레이트는 `[profile.dev.package."*"]`의 최적화 대상이 아니다.
   - 교훈: **기능 점검·성능은 Release로**(CLAUDE.md "테스트 = Debug exe"는 단위 테스트 이야기). 사용자가 "첫 실행이 오래 걸린다"고 본 것도 이 Debug 기동이었다.
2. **메모리 회수 1차가 무효**였다. 기준선을 재기 전에 올림 명령이 이미 실행되어 기준(17 MB) > 올림(8 MB)으로 뒤집혔다.
   → 타임라인을 **앱 시작 기준 절대 시각**으로 고쳤다(`at()` 헬퍼). 이어서 R4의 시험 파일이 0 바이트였던 것(heredoc의 `'n$i_'`가 미정의 변수),
   R4·R6의 "놓음"이 결과 탭을 안 닫던 것(결과 탭은 편집기 탭에 속한다 → `file.close_tab`)도 차례로 잡았다.

## 6. 저녁 — 사용자 실기에서 나온 결함 셋(Linux 첫 실사용)

사용자가 Debug 빌드로 직접 써 보다 세 가지를 보고했다. 전부 원인을 찾아 고쳤고, 마지막 하나는 구현까지 새로 했다.

### 6-1. 🔧 그리드 수정 → UPDATE가 ORA-00936 — **결과 그리드의 방언 오염**

로그에 `UPDATE DEMO_BSY SET [ATTR01_VAL] = N'AA' …`(SQL Server 문법 · 대괄호)와 `OCI Error`(Oracle 드라이버)가 한 문장에 있었다.
`grid.set_dialect`는 **접속 성공 시점**(`set_dialect_for_sess_grids`)에만 불렸고 결과가 도착할 때는 아니었다 → Oracle 결과를 띄운 뒤 편집기에서
`CONNECT mssql://…`를 실행하면 옛 결과 그리드의 방언까지 Mssql로 덮어써진다. 결과의 방언은 결과의 속성이다(DR-33) → 결과가 도착하는 두 지점
(`main.rs` 페치/재조회 · 실행)에서 **그 결과를 만든 세션의 `Sess.dialect`** 를 같이 싣도록 고쳤다.

### 6-2. 🔧 Ctrl+X = 글자는 사라지고 클립보드엔 없음 — **데이터 손실 순서 결함**

`clip_action(Cut)`이 `cut_selection()`으로 **먼저 지우고** 그 뒤 `clipboard::write_text`를 불렀다. 쓰기가 실패하면(아래 6-3) 본문에도 클립보드에도 없는 상태.
편집기·그리드 셀 편집 둘 다 **클립보드가 받아 준 뒤에만 지우도록** 순서를 뒤집었다(61 §1-7 데이터 보호 불변식).

### 6-3. ★ Linux 클립보드 = X11 selection **직접 구현**(`clipboard_x11.rs` · 추가 의존 0)

상태줄이 정확히 말하고 있었다: *Clipboard unavailable (Linux: install wl-clipboard or xclip)*. Linux 경로는 `wl-copy`/`xclip`/`xsel` **외부 프로그램**을 부르는
구조였고 이 VM엔 셋 다 없다. 사용자: *"클립보드 관련 프로그램이 없다고 실행파일 내에서 클립보드 동작이 안 되는 게 정상이야? … 이 VS Code는 정상동작하는데"* —
정상이 아니다. 클립보드는 프로그램이 아니라 프로토콜이고 창을 띄운 앱은 직접 참여할 수 있다(VS Code·Sublime이 xclip 없이 되는 이유).
Windows(`SetClipboardData`)·macOS(`pbcopy`)와 격이 달랐다.

91차 모달용으로 이미 들어온 `x11rb 0.13`으로 `CLIPBOARD` selection을 직접 쥔다: 소유권 유지 스레드(처음 복사할 때 한 번 · 1×1 InputOnly 창 ·
`TARGETS`/`UTF8_STRING`/`STRING`/`text/plain;charset=utf-8` 응답 · **INCR** 양방향) · 읽기 = `ConvertSelection` → `SelectionNotify`(1.2 s 상한).
설정 `clipboard.x11_native`(기본 켬 · 끄면 종전 CLI 폴백). 진단 `NSQL_TRACE_CLIP=1`.

**검증(상대 = python3 Gtk3 · `GDK_BACKEND=x11` 고정)**: 읽기 ✅ · 쓰기 ✅(다른 프로세스가 우리 TARGETS를 그대로 봄) · INCR 303,620 B 3조각 바이트 일치 ✅ ·
앱 실경로(`edit.select_all`→`edit.copy`) ✅ 1회 통과(추적 사슬 전부 확인) — 다만 같은 조건 재실행 2회는 **기동 명령 자체가 디스패치되지 않아**
(`[clip] copy:` 줄 없음) 판정 불가. 이건 클립보드가 아니라 자체 시험의 타이밍 문제(앞의 "덤프 3건"과 같은 계열 · Debug 첫 페인트 1.3~1.9 s).

**헛디딘 것 셋** — ① 시험 필터 `--exact`에 짧은 이름을 줘 0개 실행이 "ok"로 위장(`260 filtered out`) ② 상대편 Gtk가 Wayland 세션에서 **Wayland 백엔드**를 써
X11 `CLIPBOARD`에 닿지 않았다(read()가 실제 X11 내용 = Nautilus 파일 복사를 정확히 읽어 온 것이 단서) ③ ★ **자동 시험이 사용자의 실제 클립보드를 덮어썼다**
(사용자가 자리에서 복사한 글이 독자에 잡혔다) — 규칙 위반(CLAUDE.md §3 "클립보드를 덮어쓰는 명령을 자동 시험에 넣지 않는다"). 그 자리에서 중단.
클립보드 왕복 시험은 `--ignored`로 두고 **사용자가 자리를 비웠을 때만** 돌린다.

**남은 확인(사용자 손)**: ① 재시작 뒤 nexa-sql 안에서 복사/붙여넣기 · Ctrl+X ② nexa-sql → **VS Code(네이티브 Wayland · `--ozone-platform=wayland`)** 붙여넣기 —
mutter가 X11 소유권을 Wayland 쪽에 넘기는 다리는 **포커스 있는 창만** 통과시킨다(대조 실험: 포커스 없는 Gtk-X11 작성자도 못 넘어감) → 실제 앱이 포커스를 가진 상태로만 판정 가능
③ Oracle 결과를 띄운 채 다른 방언으로 `CONNECT`한 뒤 그리드 편집 적용.

### 6-4. 🔧 첫 실행만 ORA-00923 · 두 번째는 정상 — **ROWID 주입이 `--` 주석 줄에 붙음**(23:49 · 사용자 실기)

사용자 질의는 select 목록이 `*` 다음 줄 주석(`--\tSELECT DISTINCT A.MP_VRSN_ID`)으로 끝난다. 2급 행 식별(87 §13-7 · T-231)의 `inject`가 목록을
`trim()`해 통째로 쓰고 `, A.ROWID`를 붙인 뒤 `FROM`을 **공백 하나**로 이었다 → `--\tSELECT DISTINCT A.MP_VRSN_ID, A.ROWID FROM` 한 줄 = 주석이 FROM까지
삼킴 → ORA-00923. 두 번째가 되는 건 실패하면 "원문 복귀 + 3급"으로 캐시돼 다시는 주입하지 않기 때문(= **편집이 3급으로 강등된 채** 동작한 것 · 더 나쁜 결과).
`*` 판정도 주석 탓에 빗나가 `A.*` 치환이 안 됐다.

수정 = `code_span()`(주석·문자열 인식 스캐너 · `find_top_from`과 같은 규칙)로 목록의 **코드 구간**만 찾아 그 끝에 주입 · 원문 공백·줄바꿈·주석은 한 바이트도 안 버림 ·
`*` 판정은 코드로. 결과: `SELECT\n\tA.*, A.ROWID\n--\tSELECT DISTINCT …\nFROM …`. 시험 `inject_keeps_trailing_line_comment_out_of_the_way`(사용자 원문 그대로 + 변형 3) ·
기존 `inject_hidden_columns` 그대로 통과 · 주입문을 BISCM에 직접 실행해 확인.

## 8. 사전 검사(`SELECT COUNT(*)`)의 비용·효용 실측(01:20 · 사용자 "속도 저하·횟수 증가인지 수치로")

### 8-1. 앱 적용 경로의 왕복 수(`Runner::apply_changes` · 87 §14)

편집한 행 N개를 적용할 때 **한 트랜잭션** 안에서: ① `guard` = 행마다 같은 WHERE의 `COUNT(*)` **전부 먼저**(하나라도 ≠1이면 아무것도 안 바꿈) → ② DML N개(문장마다 영향 행 = 1 · `grid.edit_strict`) → ③ 커밋 → ④ `grid.edit_refresh=rows`면 바뀐 행을 키로 다시 읽음 N개.
= **행당 왕복 3회**(COUNT · DML · 재조회) + 커밋 1. 사전 검사만 끄는 스위치는 **없다**(`edit_strict`는 ②의 영향 행 검사 · `edit_refresh`는 ④).

### 8-2. 실측(임시 표 1,000행 · K행 갱신 · CLI `nsql run` · 3회 중앙값 · 사무실 LAN · 임시 표는 지움)

| DBMS | K | A UPDATE만 | B +COUNT 사전 검사 | C +행 재조회 | 문장당 왕복 |
|---|---:|---:|---:|---:|---:|
| Oracle 19c | 100 | 6.94 s | **13.26 s (×1.91)** | 19.56 s (×2.82) | ≈ 63 ms |
| SQL Server | 100 | 6.72 s | **13.10 s (×1.95)** | 19.34 s (×2.88) | ≈ 64 ms |
| PostgreSQL | 100 | 6.61 s | **12.96 s (×1.96)** | 19.27 s (×2.91) | ≈ 63 ms |
| PostgreSQL | 10 | 0.97 s | 1.71 s | 2.35 s | (접속 ≈ 0.4 s 포함) |
| SQLite(로컬) | 100 | 14 ms | 17 ms | 21 ms | ≈ 0.03 ms |

`server total`(서버 처리)은 전 구간 0~70 ms — **비용은 전부 네트워크 왕복**이다. 사전 검사는 행마다 왕복 1회를 그대로 얹어 적용 시간을 **약 2배**, 행 재조회까지 **약 3배**. 1행 편집(가장 흔한 경우)에서는 +63 ms로 체감이 없고, 100행 일괄 편집에서 6.9 → 13.3 s가 된다. SQLite는 무시할 수준.
(CLI는 문장마다 자동 커밋·리터럴이고 앱은 한 트랜잭션·바인드라 절대값은 다르지만, 왕복 수와 RTT가 지배하므로 배율은 같다.)

### 8-3. 효용 — 무엇을 막았나

- 사전 검사가 막는 것 = **WHERE가 0행 또는 2행 이상에 맞는 문장을 서버에 보내기 전에** 세움: 3급(전 열 비교)의 완전 중복 행 · NULL 비교 · 실수/LOB 열 · 다른 세션이 먼저 바꾼 행(낙관적 동시성). 어제(09-26) ORA-00936 사고에서도 "Pre-check failed … Nothing was changed"로 데이터가 안 바뀌었다.
- 그러나 **같은 보호는 ②만으로도 얻는다**: 한 트랜잭션 안에서 문장마다 영향 행 수를 보고 ≠1이면 되돌리면(이미 그렇게 한다) 결과는 같다. 사전 검사가 *추가로* 주는 것은 ⓐ 문장을 서버에 **아예 보내지 않음**(트리거·감사 로그·행 잠금·시퀀스 소모가 안 생김) ⓑ "N행이 맞음"이라는 **정확한 사전 메시지** ⓒ 자동 커밋 DBMS에서 되돌리기가 불가능한 드라이버 경로의 안전망(지금은 트랜잭션으로 감싸므로 해당 없음).

### 8-4. 트레이드오프 정리(결정은 사용자)

| 선택지 | 비용(행당) | 보호 | 비고 |
|---|---|---|---|
| 지금(사전 검사 + 영향 행 검사 + 행 재조회) | 왕복 3 | 최대 · 서버에 닿기 전 차단 | 100행 = 19 s |
| 사전 검사 off · 영향 행 검사 + 되돌리기(트랜잭션) | 왕복 2 | 같음(되돌림) · 다만 트리거/감사/잠금은 발생 | 100행 = 13 s |
| + 행 재조회 off(`grid.edit_refresh=local`) | 왕복 1 | 같음 · 화면은 서버 값 대신 입력 값(기본값/트리거 결과 미반영) | 100행 = 7 s |
| 1급(PK가 결과에 있음)만 사전 검사 생략 | 왕복 2~3 | PK 일치는 0/1행뿐이라 사전 검사가 잡을 게 없음 | 절충안 · 3급만 검사 |

권장(제 판단): **1급·2급(키/ROWID 일치)은 사전 검사를 생략**하고 **3급(전 열 비교)만 유지** — 3급이 바로 "2행 이상 맞을 수 있는" 유일한 경우다. 설정 키(`grid.edit_precheck = always|all_cols_only|off`)로 두면 사용자가 고를 수 있다. 결정 대기(D-226).
