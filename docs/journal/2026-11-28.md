**④ 안전 수정의 경위(데이터 보호 · 있는 그대로)** — `rebase`(적용 중단 뒤 · 고친 스크립트 뒤 다시 읽기)가 서버에 새로 생긴 항목(지난 원본에 없고 편집 모델도 모르는 것)을 편집 모델에 들이지 않아, 다음 차이 계산이 그것을 `DROP COLUMN`으로 잡았다. 개발이 ②를 V1로 돌리다가 발견했다 — 고친 스크립트로 `extra2`를 더한 뒤의 덤프에 `stmt|Danger|ALTER TABLE … DROP COLUMN extra2`. 수정 = 그런 항목을 편집 모델에 들인다(`origin = 자기 이름`) + 시험 `rebase_adopts_server_side_additions_and_keeps_pending_edits`.

이 결함은 1차 · 2차 커밋판(e32337bf · e7e4d719)에도 있었다. 그때 `rebase`로 들어가는 길은 "문장이 중간에 멈춘 뒤"뿐이어서 서버 쪽 추가분이 생기는 경우는 다른 세션의 동시 변경(같은 테이블에 컬럼 · 제약 · 인덱스를 더함)뿐이었지만, 그 경우에도 다음 적용 전 재확인(F-13)은 방금 다시 읽은 원본을 기준으로 통과하므로 **실제 위험이 있었다** — 미리보기에는 위험 문장으로 보이나, 사용자가 요청하지 않은 삭제 문장이 스크립트에 들어간다. 일어났다는 보고는 없다. 배포판(v0.10.2)에는 구조 편집기가 들어 있지 않다(1차 = 11-27 커밋).

## §3. T-526 — 생성 DDL · 객체 백업 DDL의 FK에 삭제 · 갱신 규칙 싣기(개발 구현 · 협업 검증 · 문서)

**무엇(개발 · 2파일)** — `nsql-catalog` `gen.rs` `constraint_line`의 외래 키 가지가 FK 본문 뒤에 ` ON DELETE x` · ` ON UPDATE y`를 붙인다 — 4차의 방언 사전 질의 `key_extras`(이제 `pub(crate)`)로 읽고 새 순수 함수 `fk_rules`가 꼬리를 만든다(빈 값 = 생략 · Oracle은 갱신 규칙을 붙이지 않음 · 시험 `fk_rules_tail`) · 못 읽으면 종전대로(규칙 없는 줄) · PostgreSQL은 종전처럼 `pg_get_constraintdef`. 보수적 생성 원칙([100 §5](../100-object-source-run-and-output-tab.md))의 구멍 = 종전 DDL을 그대로 실행하면 규칙이 `NO ACTION`으로 바뀌었다.

## §5. T-527 — SQL Server 생성 DDL · 객체 백업 DDL에 제약 상태 싣기 + 덧붙은 속성 한 번 읽기(개발 구현 · 협업 준비 메모 · 검증 · 문서)

**준비 메모(협업 · 개발 착수 전)** — ① 생성기에서 `key_extras`를 부르는 자리 = `constraint_line` 안(FK 줄마다 다시 질의 · §3 소견 ②) · `constraint_line`을 부르는 자리 넷(`close_table_body` · `table_with_keys` · `sub_ddl` 둘) ② SQL Server 문법(문서) = `ALTER TABLE t [WITH CHECK | WITH NOCHECK] ADD CONSTRAINT …` · `ALTER TABLE t {CHECK | NOCHECK} CONSTRAINT 이름` · FK 꼬리 순서 `… ON DELETE … ON UPDATE … NOT FOR REPLICATION` · CHECK = `CHECK NOT FOR REPLICATION (식)` ③ 실측(아래 표) ④ MySQL = `[CONSTRAINT 이름] CHECK (식) [[NOT] ENFORCED]`(8.0.16+) · 생성 DDL에 CHECK 줄 자체가 없는 것으로 보임(코드 읽기 · 실서버 없음).

실측(실서버 SQL Server 2019 · 빈 임시 테이블 · 여러 방법으로 만든 제약의 `sys.foreign_keys` / `sys.check_constraints` 플래그 · 끝에 `DROP` 뒤 남은 수 0):

| `is_disabled` · `is_not_trusted` · `is_not_for_replication` | 어떻게 만들면 나오나 | 되살리는 문장 |
|---|---|---|
| 0 · 0 · 0 | 표 안 줄 · `ADD CONSTRAINT`(= `WITH CHECK`) | 종전 그대로(표 안 줄 또는 `ADD`) |
| 0 · 1 · 0 | `WITH NOCHECK ADD`(빈 테이블이어도 신뢰 안 됨) | `ALTER TABLE … WITH NOCHECK ADD CONSTRAINT …`(표 안 불가) |
| 1 · 1 · 0 | 붙인 뒤 `NOCHECK CONSTRAINT` | `WITH NOCHECK ADD` + `ALTER TABLE … NOCHECK CONSTRAINT 이름` |
| 0 · 1 · 1 | `NOT FOR REPLICATION`을 단 모든 만들기(항상 신뢰 안 됨) | 본문에 `NOT FOR REPLICATION`(표 안 가능) |
| 1 · 1 · 1 | 위 + `NOCHECK CONSTRAINT` | 본문에 `NOT FOR REPLICATION` + `NOCHECK CONSTRAINT` |

그 밖 조합은 나오지 않았다(끈 것을 `CHECK CONSTRAINT`로 다시 켜면 0 · 1 · 0에 머물고 `WITH CHECK CHECK CONSTRAINT`라야 0 · 0 · 0) · 한 자식에서 같은 부모로 가는 FK 여럿에 연쇄 규칙을 주면 Msg 1785(연쇄 경로 여럿) = 탐침의 실수로 한 건 못 잼.

**무엇(개발 · 2파일 · `crates/nsql-catalog/src/gen.rs` · `lib.rs`)** — `KeyExtra.state`(SQL Server만 `D` 비활성 · `T` 신뢰 안 됨 · `R` `NOT FOR REPLICATION` · 다른 방언은 빈 글 = 질의에 `''` 한 열) · `constraint_line`이 덧붙은 속성을 인자로 받는다(안에서 다시 질의하지 않음) · `extras_for` = FK · CHECK가 있을 때만 테이블 DDL당 한 번(PostgreSQL은 읽지 않음) · 본문에 `NOT FOR REPLICATION`(FK = 맨 끝 · CHECK = `CHECK NOT FOR REPLICATION (식)`) · 순수 함수 `key_stmts(이름들, 본문, 상태) → (표 안 가능, ADD 문장, 뒤따르는 NOCHECK 문장)` — 부르는 자리 넷 전부 이 함수 · 시험 `key_stmts_reproduce_sql_server_states`(위 다섯 상태) · MySQL은 손대지 않음(→ T-528) · 구조 편집기의 `locked` 뜻 불변.
