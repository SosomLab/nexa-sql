## 63차 (mac) — 사용자 요청 4건

### ① "비밀번호가 없는데 연결이 되고 있어" — 분석과 조치

- **현상**: 편집기에서 `CONNECT oracle://BISCM@61.81.244.214:1521/BISCM`(비밀번호 없음)을 실행하면 접속이 됐다.
- **원인 = 자격 빌리기(`worker::fill_credentials` · 56차)**: 워커의 opener가 비밀번호 없는 스펙을 받으면 저장소(`nsql-vault`)에서 **방언·호스트·포트·DB가 같고 사용자가 같은 프로필이 정확히 하나**일 때 그 프로필의 자격을 그대로 썼다. 저장 프로필 SNOP-DB가 같은 서버·같은 계정이라 그 비밀번호로 붙은 것. "1 서버 · 1 계정" 사상의 편의로 넣었지만 사용자가 보기엔 **비밀번호 없이 접속되는 것**이라 오해와 오접속(다른 계정 프로필의 자격을 빌리는 실수)을 낳는다.
- **조치**: `fill_credentials`·`same_target` 제거 → `password_required(spec, default_dialect)` = 방언 ≠ SQLite ∧ 호스트 있음 ∧ 비밀번호 없음/빈 값 → opener가 `ErrPasswordRequired`로 거부(드라이버에 가지 않음). 저장소 프로필 이름은 `resolve_target`이 워커 전에 채우므로 영향 없음 · 접속 창 폼도 같은 opener를 타서 비밀번호 없이 Connect하면 같은 문장. `explorer_attach`의 빌리기도 제거(인라인 스펙은 이제 항상 자격을 갖는다). MC/DC `password_required_mcdc`(기준 1 + 조건 반전 4) · 52 §4·§12 D10 갱신.
- **할일 T-132**: 비밀번호를 문자열에 쓰지 않는 길 — 편집기 변수(세션 메모리만 · 로그/이력 제외) · `CONNECT`에 비밀번호가 없으면 모달 입력 · CLI 프롬프트 · 로그인 창 `session_pw`와 한 저장소.

### ② No connection이 공유로 되돌아감(fail-over 보완)

- **현상**: 공유 연결 1 + 전용 탭에서 표식 메뉴 **No connection**을 고르면 잠시 미연결이었다가 공유 연결로 묶였다.
- **원인**: `RunEvent::Disconnected` 처리의 "공유 모드 ∧ 전용 ∧ !idle_closed → `closing`"이 스크립트 `DISCONNECT`용 복귀 규칙인데, 배지 메뉴의 해제(`disconnect_private_as(tab, keep=true)`)도 같은 이벤트를 받아 세션을 거두고 `sync_sess`가 공유로 묶었다.
- **조치**: 조건에 `!user_disconnected` 추가 — 사용자가 명시적으로 고른 미연결은 그대로 남는다. 툴바 Disconnect(keep=false)는 종전대로 공유 복귀 · 전용 직접 해제 기능은 두지 않음(사용자 "필요 없음"). 52 §12 ②의 호스트 분기가 조건 4개가 됐다 → T-122 순수 함수화 후보 그대로.
