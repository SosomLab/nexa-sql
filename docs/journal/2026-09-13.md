## 7차 (win) — ★ 사용자 Oracle 19c 실서버 실기 · 결함 1건 수정 · 순수 Rust thin 스파이크 (사용자 요청)

**요청**(사용자): 19c 접속 정보(192.168.0.58:1521/BISCM · BISCM) 제공 → 테스트에 사용 · *"개발 가능한 부분은 먼저 정리해서 진행"* · *"Rust용 오라클·SQL Server 클라이언트로는 연결이 안 되는 거야?"* · *"다른 DBMS 접속도 확인"*.

**실기(프로필 경로)**: `nsql conn add biscm oracle://…` → `%APPDATA%\nexa-sql\profiles\biscm.conf`(비밀번호 봉투) → `nsql conn test biscm` **OK 1.236s**(kubo `oracle` + Instant Client 23.9 · 서버 19.3 EE). `examples/it-oracle.sql` **전부 통과**(세션 변수 · `EXEC SELECT … INTO` 다중 OUT · REF CURSOR PRINT · DBMS_OUTPUT). `golden-session-vars.sql`은 통계 수집·프로시저 호출이 있어 실행하지 않고 `plan` 양 방언만 확인(불변).

**실서버가 잡은 결함**: `EXEC :V_CNT := (SELECT COUNT(*) FROM user_tables)` → PLS-00103. PL/SQL은 식 안의 서브쿼리를 허용하지 않는다. `wrap_exec(Oracle)`이 우변에 `(SELECT`/`(WITH`가 있으면 `BEGIN SELECT <rhs> INTO :V FROM DUAL; END;`로 재작성(커밋 41acc2a · +4 단언 · 재확인 V_CNT = 442).

**질문 답 — Rust 클라이언트**: 지금 접속에 쓴 것이 Rust 드라이버(kubo `oracle`)다. 단 ODPI-C 기반이라 Instant Client가 런타임에 필요하다(이 기기 `C:\Oracle\instantclient_23_9`). SQL Server `tiberius`는 순수 Rust(클라이언트 불요 · integration에서 검증됨).
**thin 스파이크**(scratchpad · 저장소 밖): 공식 순수 Rust `oracledb` 26.0.0-beta.3 — **PATH에서 Instant Client를 빼고 19c 접속 157ms · 조회 ✓**(OCI 1.2s 대비 8배). 사용자 Python 프로젝트(`2026-sebang-snop-db/db.py`)도 thin 모드 기본 — 같은 서버에서 thin이 실무로 쓰이고 있다. ★ 그러나 **docs.rs 공개 API에 OUT/IN OUT 바인드 · REF CURSOR · DBMS_OUTPUT 회수가 없다**(`Connection`/`Statement` = execute/query/query_row(+named) · call_timeout · LOB). 세션 변수 엔진의 `SELECT … INTO :V` · 프로시저 OUT · `PRINT rc`가 OUT 바인드에 의존하므로 **thin은 아직 주 드라이버 불가** → DR-12 유지, 교체 조건을 "OUT 바인드·REF CURSOR 지원"으로 구체화(D-22). thin이 오면 Oracle SxS([22 §4-1](../22-driver-extensions.md)) 필요도 레거시(11g/12.1 → thin 하한 12.1)로 줄어든다.

**다른 DBMS**: 이 기기에 Docker·DB 서비스 없음 · 사용자 DB 프로젝트는 Oracle 전용. MSSQL·PG 실서버는 **접속 정보 필요**(스크린샷의 PostgreSQL 192.168.0.60:5433/matrixdb2는 PG 드라이버가 M4라 아직 접속 불가). MSSQL은 integration(SQL Server 2022 컨테이너)에서 이미 5/5.

**개발 가능한 부분 정리(다음 착수 순)**: ① **T-27** `nsql-driver-rpc` 프로토콜 + sqlite-rpc 참조 구현(외부 자원 불요 · 로컬 테스트) → ② T-28 `drivers/` 보관·`nsql driver list/rm` → ③ T-29 GitHub 다운로드(드라이버 릴리스 저장소 D-19 필요) → ④ T-31 접속 대화상자(GUI 실기 필요). PG 드라이버(M4 · `tokio-postgres`)는 접속 정보가 오면 실서버 검증까지 한 번에 가능.

**기존 자산 확인(재발명 금지)**: 봉투 = nexa-clip `nclip-store/src/sealed.rs`(ChaCha20-Poly1305 · 도메인 분리) 이식 · 키 계층 = `nclip-store/src/keys.rs`(마스터 간접 한 겹) 차용 · 폴더·직렬화·원자적 쓰기 = `nexa-conf` 그대로. 암호화 3 crate는 clip 원장과 동일 판(자체 구현 금지 부류) → [10 §4](../10-decision-record.md).

**설계 판단**:
- **비밀번호만 암호화**, 호스트·사용자명은 평문 — `conn list`가 보여 줘야 하는 값. 도메인에 프로필 이름을 넣어 봉투 바꿔치기를 막는다(테스트 `secret_bound_to_profile_name`).
- **기기 키 보호는 OS별로 다르게**: Windows DPAPI(`crypt32` 직접 FFI · UI 금지 플래그 · 앱 엔트로피) → 같은 계정만 푼다. mac/linux는 0600 평문(정직한 한계 · D-18). 디스크에 평문 키가 없음을 테스트로 고정(`create_then_reload_same_key`).
- **여러 인스턴스**(요청 ④): 파일 저장소 + 메모리 캐시 없음이라 기본 성립. 위험은 **동시 첫 실행에서 기기 키 둘**이 생기는 것 → `create_new`로 단일 생성 · 진 쪽은 재시도 후 읽기. 8 스레드 경합 테스트 `concurrent_first_run_yields_single_key` ✓.
- 프로필 이름 규칙(`[A-Za-z0-9_.-]`)이 접속 문자열과 겹치지 않아 `-c prod`를 그대로 쓴다. 이름 꼴인데 없으면 **오류**(exit 2) — 오타를 접속 문자열로 오해하지 않게.
- `nsql-run`에 `Resolver` 훅 — 스크립트 `CONNECT prod`(사용자명만 있는 스펙)를 프로필로 푼다. `parse_target`이 기본 방언을 채우므로 호스트는 `is_profile_name`을 먼저 본다.
- 숨김 입력은 외부 crate 없이: Windows `SetConsoleMode`(ECHO 끔) · unix `stty -echo`.

**산출**: `crates/nsql-vault`(lib · sealed · devkey — 13 테스트) · `nsql-run` Resolver(+1 테스트) · `nsql-cli` `conn list|add|show|rm|test|path` + `-p` + `term.rs` · GUI 이름 칸 + Save 버튼 + 접속 칸 이름 해석 + 시작 시 저장 프로필 안내 · 문서 [21](../21-connection-profiles.md).
