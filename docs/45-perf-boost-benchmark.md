# 45 · 실행 속도 향상(`perf.boost`) 켬/끔 성능 비교 (2026-09-17 · Windows 실측)

> **요청**(사용자 09-17): *"실행속도향상을 켠 상태와 끈 상태에 대한 다양한 측면의 성능 비교 · 실 연결은 61.81.244.214:1521 · MSSQL은 등록된 SQL Server · 별도 문서에 비교표로."*
> **설계**: [39 §4-6](39-resource-governance.md) · **측정 스크립트**: `scratchpad/bench-boost.ps1`(세션 임시 · 저장소 이식 = T-90e) · 원자료 `target/bench-boost.csv`.

## 0. 결론 다섯 줄

1. **유휴 자원이 줄었다**: 유휴 10초 CPU 시간 125ms → **0ms**(캐럿 깜빡임·페이드 타이머 0) · 스레드 14 → **11** · 핸들 269 → **225** · 작업 집합 26.6 → **22.3 MB** · 사설 메모리 9.6 → **8.1 MB**.
2. **기동 시간은 같다**(창 핸들 생성까지 155 ↔ 156 ms): 기동 경로에는 향상 대상이 거의 없다(둘째 창·git·아이콘은 기동 뒤 일어남). 기동 자체의 단축은 T-102(링크·초기화 순서) 몫.
3. **질의 실행·페치 시간은 같다**(Oracle COUNT 18ms · 200행 execute 6~7ms + fetch 22ms · MSSQL 200행 37ms): 향상 모드는 설계대로 **실행 경로(왕복 수·페치 크기)를 건드리지 않는다**. 네트워크 쪽 이득은 실행이 아니라 **백그라운드 트래픽**(신호등 60s → 300s · ICMP 0 · 라이브 로그 폴링 0)에서 난다.
4. **체감 효과**는 애니메이션·페이드·툴팁·아이콘 래스터·우클릭 클립보드 읽기가 0이 되는 데서 온다 — 수치로는 유휴 CPU 0과 스레드 −3이 그 증거이고, 입력 지연은 이번 도구로 재지 않았다(T-90e).
5. 결과에 영향이 있는 키(행 수·페치 크기·타임아웃)는 의도적으로 제외했으므로 **질의 결과·시간은 두 모드에서 동일**해야 하고, 실측이 그것을 확인한다.

| 항목 | 값 |

렌더링 8(애니메이션 off · fps 30 · 캐럿 깜빡임 off · 페이드/슬라이드 0 · hover 의도 120ms) · 아이콘/부가 표시 7(탐색기·OS 파일·메뉴 아이콘 off · 탭 툴팁 off · 미니맵 off · 선택어 강조 off · 빈 폴더 셰브론 프로브 off) · I/O·기동 4(git off · HTML 복사 off · 우클릭 클립보드 읽기 off · 시작 시 로그 창 off) · 메모리 1(아이콘 캐시 128) · 폴링/스레드 6(프로브 300s·동시 1·재시도 1·ICMP off · Oracle 라이브 로그 off·5000ms). 제외 목록과 근거는 [39 §4-6](39-resource-governance.md).

## 3. 해석 · 다음

- 목표 ①(기동)은 이 스위치로는 안 움직인다 → **T-102**(링크 옵션 · 초기화 지연 · 폰트/설정 읽기 순서)에서 다룬다.
- 목표 ②(네트워크)는 실행 경로가 아니라 백그라운드 트래픽 감소로 나타난다(신호등 60s → 300s · ICMP 0) — 이 도구로는 안 보이고 [26 §8](26-performance-architecture.md) 표의 상한이 근거.
- 목표 ③④⑤(스레드·메모리·체감)는 수치로 확인됐다(스레드 −3 · 메모리 −16% · 유휴 CPU 0).
- **미측정**: 입력 지연·프레임 시간(체감의 직접 지표) · 접속 1개 열린 상태의 유휴(라이브 로그·프로브 스레드 차이가 여기서 커진다) · 대용량 결과(155k행) 전체 조회 뒤 메모리 회수. → T-90e(`scripts/bench-boost.ps1`로 이식 · 접속 상태 시나리오 추가).
